Expression trees представляют код в виде древовидной структуры объектов, позволяют исследовать, преобразовывать и компилировать выражения во время выполнения, а компилятор C# генерирует их при присваивании expression lambda переменной типа `Expression<TDelegate>`.[cite:1][cite:3]

## Базовая ментальная модель

Expression tree — это не исполняемый IL и не обычный делегат, а объектная модель кода в памяти; выполнить дерево напрямую нельзя, сначала его нужно превратить в делегат через `Compile()`, если дерево представляет лямбду.[cite:1][cite:3]

```text
C# lambda
   |
   +--> Func<T> ----------------> compiled delegate
   |
   +--> Expression<Func<T>> ----> object graph (code as data)
                                      |
                                      +--> inspect
                                      +--> transform
                                      +--> translate
                                      +--> compile
```

## 1. Основы и ментальная модель

### 1. Что такое expression tree в C#?
**Ответ:** Expression tree — это объектное представление кода в памяти, где каждая операция, константа, параметр или вызов метода выражены отдельным узлом дерева. В отличие от обычного делегата, дерево можно анализировать, переписывать и транслировать в другие формы, например в SQL у LINQ-провайдеров.[cite:1][cite:3]

**Ресурсы:** Microsoft Learn: Expression Trees; `Expression<TDelegate>` API.[cite:1][cite:3]

**Схема:** `Lambda -> Expression<TDelegate> -> tree of nodes -> inspect/transform/compile`.

### 2. Чем expression tree отличается от delegate?
**Ответ:** Делегат — это уже исполняемый код, а expression tree — это описание кода как данных. Делегат отвечает на вопрос «как выполнить», а дерево — «из чего состоит выражение», поэтому LINQ to Objects принимает `Func<T,...>`, а LINQ-провайдеры чаще используют `Expression<Func<T,...>>` для анализа и перевода.[cite:1][cite:3]

**Ресурсы:** Microsoft Learn: Expression Trees; `Expression<TDelegate>` API.[cite:1][cite:3]

**Схема:** `Func<T,bool> => invoke only`, `Expression<Func<T,bool>> => inspect + maybe compile`.

### 3. Почему expression trees часто описывают как “code as data”?
**Ответ:** Потому что они сохраняют структуру кода в виде объектов `Expression` и производных типов. Это позволяет обрабатывать код так же, как любую другую структуру данных: обходить, сравнивать, трансформировать и кэшировать.[cite:1][cite:6]

**Ресурсы:** Microsoft Learn: Expression Trees; `System.Linq.Expressions` namespace.[cite:1][cite:6]

### 4. Когда компилятор C# сам строит expression tree?
**Ответ:** Когда expression lambda присваивается переменной, полю или параметру типа `Expression<TDelegate>`. При этом компилятор не создает обычный исполняемый делегат, а генерирует код построения дерева выражения.[cite:1][cite:3]

**Ресурсы:** Microsoft Learn: Expression Trees; `Expression<TDelegate>` API.[cite:1][cite:3]

### 5. Почему statement lambda не может быть автоматически преобразована в expression tree?
**Ответ:** Компилятор C# генерирует expression trees только из expression lambdas, то есть из однострочных лямбд-выражений. Многострочные statement lambdas не поддерживаются этим механизмом напрямую, потому что стандартная модель expression trees ориентирована прежде всего на выражения, а не на произвольные синтаксические конструкции языка.[cite:1]

**Ресурсы:** Microsoft Learn: Expression Trees.[cite:1]

**Схема:** `x => x + 1` ✅, `x => { var y = x + 1; return y; }` ❌ для автоматического преобразования компилятором.[cite:1]

### 6. Какие ключевые сценарии использования expression trees встречаются в реальных проектах?
**Ответ:** Наиболее типичны динамическая генерация предикатов, LINQ-провайдеры, ORM, мокинг-фреймворки, правила фильтрации, сортировка и построение DSL поверх C#. В официальной документации Microsoft отдельно подчеркиваются Entity Framework и Moq как характерные примеры использования expression trees.[cite:1]

**Ресурсы:** Microsoft Learn: Expression Trees.[cite:1]

### 7. Почему expression trees особенно важны для LINQ-провайдеров?
**Ответ:** Потому что провайдеру нужен не результат выполнения функции, а ее структура. Получив дерево, провайдер может разобрать его и перевести в другой язык исполнения, например SQL, вместо запуска кода в CLR.[cite:1]

**Ресурсы:** Microsoft Learn: Expression Trees.[cite:1]

### 8. Что является корнем иерархии expression tree API?
**Ответ:** Базовым абстрактным типом является `Expression`, который служит корнем всей иерархии узлов. Конкретные элементы вроде `BinaryExpression`, `MethodCallExpression`, `ConstantExpression` и других наследуются от него.[cite:6]

**Ресурсы:** `System.Linq.Expressions` namespace docs.[cite:6]

### 9. Что такое `Expression<TDelegate>` и зачем нужен generic-вариант?
**Ответ:** `Expression<TDelegate>` представляет типизированную лямбду в форме дерева выражения. Generic-параметр задает сигнатуру делегата, что делает API удобнее и безопаснее по типам, чем работа только с нетипизированным `LambdaExpression`.[cite:3]

**Ресурсы:** `Expression<TDelegate>` API docs.[cite:3]

### 10. Почему expression trees называют immutable?
**Ответ:** Потому что после создания узлы дерева не изменяются на месте. Для модификации нужно построить новое дерево, обычно копируя старое и подменяя только нужные узлы, что особенно хорошо ложится на паттерн visitor.[cite:1][cite:2]

**Ресурсы:** Microsoft Learn: Expression Trees; Building Expression Trees.[cite:1][cite:2]

### 11. Что это означает на практике для архитектуры кода?
**Ответ:** Нельзя «поправить» один узел внутри уже существующего дерева; вместо этого строится новый граф выражений. Поэтому библиотеки трансформации почти всегда реализуют copy-on-write подход: если дочерние узлы не изменились, родительский узел можно переиспользовать, иначе создается новый.[cite:1][cite:2]

**Ресурсы:** Microsoft Learn: Expression Trees; Building Expression Trees.[cite:1][cite:2]

### 12. Какой самый важный conceptual difference между выражением и деревом выражения на собеседовании?
**Ответ:** Выражение в C# — это часть исходного кода, а expression tree — это runtime-модель этого выражения. Собеседующий обычно ожидает услышать, что tree нужен не ради выполнения самого по себе, а ради анализа, трансляции и генерации поведения.[cite:1][cite:3]

**Ресурсы:** Microsoft Learn: Expression Trees; `Expression<TDelegate>` API.[cite:1][cite:3]

## 2. Типы узлов и объектная модель

### 13. Какие узлы встречаются чаще всего в прикладном коде?
**Ответ:** Чаще всего используются `ParameterExpression`, `ConstantExpression`, `BinaryExpression`, `MemberExpression`, `MethodCallExpression`, `UnaryExpression` и `LambdaExpression`. Именно из этих типов обычно собираются фильтры, сортировки и проекции для ORM и query builders.[cite:2][cite:6]

**Ресурсы:** Building Expression Trees; `System.Linq.Expressions` namespace.[cite:2][cite:6]

### 14. Что хранит `ParameterExpression`?
**Ответ:** Он представляет параметр лямбды или локальную переменную в некоторых конструкциях API. Важно, что один и тот же логический параметр должен быть представлен одним и тем же объектом `ParameterExpression`, иначе сравнение и связывание параметров нарушатся.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

### 15. Что такое `ConstantExpression` и где бывают подводные камни?
**Ответ:** Это узел, представляющий константное значение. Подводные камни начинаются там, где разработчик случайно захватывает крупный объект, сервис или замыкание, и затем это дерево оказывается трудно переводимым в SQL, плохо сериализуемым или неожиданно удерживает память.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

### 16. Что представляет `BinaryExpression`?
**Ответ:** Это узел бинарной операции, например сложения, сравнения или логической комбинации. Такие узлы лежат в основе предикатов вида `x => x.Age > 18 && x.IsActive`.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

### 17. Что представляет `MethodCallExpression`?
**Ответ:** Это вызов метода в дереве выражения. Он особенно важен в LINQ, потому что многие query-пайплайны — это именно вложенные вызовы `Where`, `Select`, `OrderBy` и пользовательских методов.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

### 18. Почему `MemberExpression` критичен для ORM и маппинга?
**Ответ:** Потому что он описывает доступ к полю или свойству, а значит провайдер может понять, какой именно член типа запрашивается. Именно через такие узлы часто извлекают имена свойств для динамической сортировки, валидации и конфигурации.[cite:6]

**Ресурсы:** `System.Linq.Expressions` namespace docs.[cite:6]

### 19. Что такое `LambdaExpression`?
**Ответ:** Это узел, представляющий лямбда-выражение как оболочку над телом и списком параметров. Выполнить можно только дерево, которое представляет лямбду, либо сначала нужно обернуть произвольное выражение в лямбду.[cite:9][cite:3]

**Ресурсы:** Executing Expression Trees; `Expression<TDelegate>` API.[cite:9][cite:3]

### 20. Для чего нужен `UnaryExpression`?
**Ответ:** Он покрывает операции над одним операндом, такие как `Convert`, `Not`, `Negate` и некоторые другие. На практике он часто всплывает там, где value type боксится в `object`, либо при явных и неявных преобразованиях типов внутри дерева.

**Ресурсы:** `System.Linq.Expressions` namespace docs.[cite:6]

### 21. Что показывает свойство `NodeType`?
**Ответ:** Оно указывает вид узла через `ExpressionType`, например `Add`, `Call`, `Equal`, `Lambda` и так далее. Именно с `NodeType` обычно начинается ручной анализ дерева и написание переводчиков.[cite:8]

**Ресурсы:** Interpret Expressions.[cite:8]

### 22. Зачем нужно свойство `Type` у каждого узла?
**Ответ:** Оно показывает CLR-тип результата данного выражения. Это крайне важно при построении деревьев вручную, потому что несогласованные типы ломают выражение либо заставляют явно добавлять `Expression.Convert`.

**Ресурсы:** `System.Linq.Expressions` namespace docs; Building Expression Trees.[cite:6][cite:2]

### 23. Почему важно различать `ExpressionType.AndAlso` и `ExpressionType.And`?
**Ответ:** Первый отражает короткое замыкание логического `&&`, а второй — побитовое или не-short-circuit поведение `&`. Для query translation и генерации предикатов это важно, потому что семантика вычисления и потенциальная переводимость различаются.

**Ресурсы:** `System.Linq.Expressions` namespace docs.[cite:6]

### 24. Чем `MemberExpression` отличается от `MethodCallExpression` при чтении дерева?
**Ответ:** `MemberExpression` отражает доступ к полю или свойству, а `MethodCallExpression` — вызов метода. Для провайдера это разные семантические категории: свойство часто переводимо в колонку, а метод — только если есть известный mapping.

**Ресурсы:** `System.Linq.Expressions` namespace docs.[cite:6]

## 3. Построение деревьев вручную

### 25. Как вручную построить дерево для `() => 1 + 2`?
**Ответ:** Сначала создаются leaf nodes через `Expression.Constant`, затем узел `Expression.Add`, а потом все оборачивается в `Expression.Lambda`. Это канонический пример из Microsoft Learn, показывающий принцип построения от листьев к корню.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

**Схема:** `Constant(1) + Constant(2) -> Add -> Lambda`.[cite:2]

### 26. Почему деревья строятся снизу вверх?
**Ответ:** Из-за неизменяемости и из-за дизайна API: конструкторы узлов принимают дочерние элементы как аргументы. Пока не созданы листья и промежуточные части, невозможно собрать родительские узлы.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

### 27. Как вручную построить предикат `num => num < 5`?
**Ответ:** Нужно создать `ParameterExpression` для `num`, `ConstantExpression` для `5`, затем `Expression.LessThan`, и после этого завернуть все в `Expression.Lambda<Func<int,bool>>`. Этот пример также приведен в официальной документации как базовый шаблон ручного построения предиката.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

### 28. Когда при ручной сборке нужен Reflection?
**Ответ:** Когда нужно представить вызов конкретного метода, например `Math.Sqrt`, и получить `MethodInfo`, который затем передается в `Expression.Call`. Это один из наиболее частых практических сценариев ручного построения дерева.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

### 29. Зачем проверять результат `GetMethod` на null при построении дерева?
**Ответ:** Потому что ошибка в имени метода или сигнатуре проявится не на этапе компиляции, а уже во время выполнения. Microsoft в примере с `Math.Sqrt` явно показывает проверку и выбрасывание исключения, если метод не найден.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

### 30. Как вручную собрать выражение расстояния `(x, y) => Math.Sqrt(x*x + y*y)`?
**Ответ:** Нужно создать два `ParameterExpression`, затем два `Multiply`, затем `Add`, потом достать `MethodInfo` для `Math.Sqrt` и собрать `Expression.Call`, а в конце — `Expression.Lambda`. Этот пример полезен тем, что показывает комбинацию параметров, бинарных операций и вызова метода в одном дереве.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

### 31. Почему важно переиспользовать один и тот же объект `ParameterExpression` в пределах одного логического параметра?
**Ответ:** Потому что идентичность параметров определяется не только именем, но и самим объектом. Если случайно создать два разных экземпляра для «одного и того же» параметра, получится логически некорректное дерево, которое может не скомпилироваться или вести себя неожиданно.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

### 32. Можно ли построить дерево в одну строку без промежуточных переменных?
**Ответ:** Да, API это позволяет, и Microsoft показывает такой пример для `1 + 2`. Но на практике для сложных выражений такой стиль ухудшает читаемость, отладку и переиспользование промежуточных узлов.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

### 33. Какой частый anti-pattern при ручном построении tree builder’ов?
**Ответ:** Смешивать бизнес-логику с низкоуровневым созданием узлов так, что итоговый код трудно тестировать и расширять. Лучше выделять фабрики выражений, composable helper methods и явные этапы: создание параметров, построение тела, финальная упаковка в лямбду.

**Ресурсы:** Building Expression Trees; Expression Trees overview.[cite:2][cite:1]

### 34. Что делать, если типы операндов не совпадают при `Expression.Equal`, `Add` и подобных вызовах?
**Ответ:** Обычно нужно явно привести один из операндов через `Expression.Convert`. Это часто нужно при построении универсальных фильтров, где значение приходит как `object`, а свойство модели — value type или nullable type.

**Ресурсы:** `System.Linq.Expressions` namespace docs.[cite:6]

### 35. Почему построение сложных деревьев через API считается более многословным, чем обычный C# код?
**Ответ:** Потому что API работает на уровне явных узлов, а не языкового синтаксиса. Документация Microsoft прямо демонстрирует, что даже простой факториал требует значительно более длинного и технически насыщенного кода, чем обычная лямбда или метод.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

## 4. Выполнение и компиляция

### 36. Можно ли выполнить любое expression tree напрямую?
**Ответ:** Нет, выполнить напрямую можно только дерево, представляющее лямбду, то есть `LambdaExpression` или `Expression<TDelegate>`. Если есть произвольное выражение, его сначала нужно обернуть в лямбду, а затем вызвать `Compile()`.[cite:9]

**Ресурсы:** Executing Expression Trees.[cite:9]

### 37. Что делает `Compile()`?
**Ответ:** `Compile()` преобразует дерево лямбды в исполняемый делегат, генерируя IL для выполнения в .NET runtime. После этого результат можно вызывать как обычный delegate.[cite:9]

**Ресурсы:** Executing Expression Trees.[cite:9]

### 38. Что происходит, если вызвать `Compile()` слишком часто для одинаковых деревьев?
**Ответ:** Это обычно приводит к лишним накладным расходам на компиляцию и может ухудшать производительность. В практическом коде часто применяют кэширование уже скомпилированных делегатов по ключу, описывающему структуру выражения.

**Ресурсы:** Executing Expression Trees.[cite:9]

### 39. Почему нельзя бездумно компилировать выражения перед передачей в ORM?
**Ответ:** Потому что после компиляции провайдер теряет структуру дерева и получает только делегат, который уже нельзя перевести в SQL. Для `IQueryable` чаще нужен именно объект `Expression`, а не готовая функция.[cite:1][cite:9]

**Ресурсы:** Expression Trees overview; Executing Expression Trees.[cite:1][cite:9]

### 40. Чем отличается `Compile()` от интерпретации дерева провайдером?
**Ответ:** `Compile()` создает делегат для выполнения в CLR, а провайдер вроде EF Core обычно сам разбирает дерево и транслирует его в другой язык или план выполнения. Это два принципиально разных сценария потребления одного и того же дерева.[cite:1][cite:9]

**Ресурсы:** Expression Trees overview; Executing Expression Trees.[cite:1][cite:9]

### 41. Когда полезно компилировать выражение в пользовательской библиотеке?
**Ответ:** Когда выражение используется локально в памяти, например для быстрого вызова accessor’а, predicate’а, компаратора или правила. Но если дерево еще нужно анализировать или передавать провайдеру, компиляция должна быть последним этапом.[cite:9]

**Ресурсы:** Executing Expression Trees.[cite:9]

### 42. Почему важно отличать `Expression<Func<T,bool>>` от `Func<T,bool>` в публичном API?
**Ответ:** Потому что это выбор между анализируемым описанием и уже готовой функцией. Для in-memory коллекций оба варианта могут быть допустимы, но для провайдеров и фреймворков от этого зависит сама возможность трансляции и оптимизации.[cite:1][cite:3]

**Ресурсы:** Expression Trees overview; `Expression<TDelegate>` API.[cite:1][cite:3]

### 43. Можно ли преобразовать произвольный узел в исполняемый код?
**Ответ:** Да, но обычно только после оборачивания в `Expression.Lambda<TDelegate>` или `Expression.Lambda`, указав нужные параметры. Официальная документация прямо рекомендует этот путь для деревьев, которые сами по себе не являются лямбдами.[cite:9]

**Ресурсы:** Executing Expression Trees.[cite:9]

### 44. Как объяснить на собеседовании цену `Compile()`?
**Ответ:** Это не «бесплатный cast», а генерация исполняемого представления дерева. Поэтому `Compile()` уместен для редко меняющихся выражений, которые затем будут многократно вызываться, а для одноразовых сценариев может оказаться лишним оверхедом.[cite:9]

**Ресурсы:** Executing Expression Trees.[cite:9]

## 5. Обход, анализ и ExpressionVisitor

### 45. Как обычно анализируют expression tree?
**Ответ:** Либо вручную через switch/if по `NodeType` и конкретным типам узлов, либо через наследование от `ExpressionVisitor`. Microsoft описывает общий подход как рекурсивный обход от корня к дочерним узлам с определением типа каждого узла.[cite:8]

**Ресурсы:** Interpret Expressions.[cite:8]

### 46. Почему дерево удобно обходить рекурсивно?
**Ответ:** Потому что каждый узел — это `Expression`, а многие узлы содержат дочерние `Expression`, образуя естественную иерархию. Такая форма хорошо ложится на depth-first traversal и visitor pattern.[cite:8]

**Ресурсы:** Interpret Expressions.[cite:8]

### 47. Когда достаточно ручного обхода, а когда лучше `ExpressionVisitor`?
**Ответ:** Ручной обход подходит для простого извлечения одного факта, например имени свойства. `ExpressionVisitor` лучше, когда нужно системно обрабатывать много типов узлов, делать переписывания и сохранять расширяемость кода.[cite:8][cite:15]

**Ресурсы:** Interpret Expressions; `ExpressionVisitor.VisitAndConvert` API.[cite:8][cite:15]

### 48. Что дает `ExpressionVisitor` кроме удобства?
**Ответ:** Он стандартизирует copy-on-write трансформации: обходит дерево, посещает дочерние узлы и при необходимости возвращает новый узел того же типа. Это упрощает безопасное переписывание immutable-структур.

**Ресурсы:** Expression Trees overview; `ExpressionVisitor.VisitAndConvert` API.[cite:1][cite:15]

### 49. Для чего нужен `VisitAndConvert`?
**Ответ:** Этот метод посещает выражение и приводит результат обратно к исходному типу выражения. Он полезен в visitor’ах, где нужно сохранить строгий тип конкретного поддерева после трансформации.[cite:15]

**Ресурсы:** `ExpressionVisitor.VisitAndConvert` API.[cite:15]

### 50. Как выглядит типичный пайплайн visitor-based rewrite?
**Ответ:** Сначала visitor находит интересующие узлы, затем рекурсивно посещает дочерние части, после чего возвращает либо исходный узел, если изменений нет, либо новый узел с замененными потомками. Такой подход напрямую следует из неизменяемости expression trees.[cite:1][cite:15]

**Ресурсы:** Expression Trees overview; `ExpressionVisitor.VisitAndConvert` API.[cite:1][cite:15]

**Схема:**
```text
Visit(node)
  -> visit children
  -> compare old/new children
  -> return same node or rebuilt node
```

### 51. Как извлечь имя свойства из выражения `x => x.Name`?
**Ответ:** Обычно проверяют, что тело — это `MemberExpression`, а затем берут `Member.Name`. На практике часто нужно еще обработать случай с `UnaryExpression`, если expression было приведено к `object` и свойство value type было обернуто в `Convert`.

**Ресурсы:** Interpret Expressions; `System.Linq.Expressions` docs.[cite:8][cite:6]

### 52. Почему доступ к свойству через `x => (object)x.Id` сложнее, чем `x => x.Name`?
**Ответ:** Потому что value type `Id` часто попадает в дерево как `Convert(MemberExpression, typeof(object))`. Если анализатор не умеет снимать внешний `UnaryExpression`, он ошибочно решит, что тело — не свойство.

**Ресурсы:** `System.Linq.Expressions` docs; Interpret Expressions.[cite:6][cite:8]

### 53. Как распознать цепочку `x.Customer.Address.City`?
**Ответ:** Это обычно вложенные `MemberExpression`, где `Expression` у внешнего `MemberExpression` указывает на предыдущий доступ к члену. Анализатор обычно разматывает цепочку назад до `ParameterExpression`, собирая путь сегмент за сегментом.

**Ресурсы:** Interpret Expressions; `System.Linq.Expressions` docs.[cite:8][cite:6]

### 54. В чем польза собственного pretty-printer для expression trees?
**Ответ:** Он резко упрощает отладку динамически генерируемых предикатов и переводчиков. Вместо чтения сложной объектной структуры можно получить компактное представление дерева в виде псевдо-C# или структурированной схемы.

**Ресурсы:** Interpret Expressions.[cite:8]

### 55. Какая ошибка часто встречается при написании собственного visitor’а?
**Ответ:** Разработчик переопределяет только нужный ему метод, но забывает корректно обходить дочерние узлы или не вызывает базовую реализацию там, где это нужно. В результате поддеревья перестают посещаться, и rewrite работает частично.

**Ресурсы:** Interpret Expressions; `ExpressionVisitor.VisitAndConvert` API.[cite:8][cite:15]

## 6. Ограничения языка и unsupported constructs

### 56. Поддерживают ли expression trees `await` и `async` lambdas?
**Ответ:** Нет, expression trees не могут содержать `await` и `async` lambda expressions. Это одно из официально перечисленных ограничений модели expression trees.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 57. Почему важно знать ограничения expression trees на собеседовании?
**Ответ:** Потому что это отделяет человека, который «видел LINQ», от человека, который понимает границы модели. Часто именно на этих ограничениях строятся вопросы о том, почему не переводится тот или иной запрос или почему определенная lambda не компилируется в `Expression<T>`.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 58. Поддерживаются ли statement-bodied lambdas?
**Ответ:** Нет, компилятор не генерирует expression trees из statement lambdas. Для сложной логики приходится либо оставаться в delegate-мире, либо строить дерево вручную через API выражений.[cite:1][cite:2]

**Ресурсы:** Expression Trees overview; Building Expression Trees.[cite:1][cite:2]

### 59. Поддерживаются ли pattern matching и switch expressions?
**Ответ:** Нет, в официальном списке ограничений прямо указаны pattern matching `is` и pattern matching `switch` expression как неподдерживаемые элементы для expression trees.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 60. Можно ли использовать tuple literals и tuple equality внутри expression trees?
**Ответ:** Нет, tuple literals, tuple conversions, а также tuple `==` и `!=` перечислены среди неподдерживаемых конструкций. Это важно помнить при попытке вынести современные языковые идиомы в LINQ-провайдеры.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 61. Поддерживаются ли `dynamic` операции?
**Ответ:** Нет, `dynamic` операции входят в список неподдерживаемых конструкций. Expression trees предназначены для статически описываемых операций над известными узлами и типами, а не для позднего связывания уровня `dynamic`.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 62. Можно ли использовать null-propagation `?.` в expression trees?
**Ответ:** Нет, null propagating operator указан в списке неподдерживаемых элементов. Если нужна аналогичная семантика, ее приходится выражать через более старые конструкции или обрабатывать на уровне переводчика.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 63. Почему новые возможности C# не всегда «видны как есть» в expression trees?
**Ответ:** Microsoft прямо говорит, что многие новые language features либо отображаются через более ранний эквивалентный синтаксис, либо вовсе недоступны. Это сделано в том числе для обратной совместимости существующих библиотек, которые интерпретируют деревья.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 64. Почему нельзя просто добавить новые node types под каждую новую фичу языка?
**Ответ:** Потому что появление новых типов узлов было бы breaking change для библиотек, интерпретирующих expression trees. По этой причине модель стараются не расширять таким способом.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 65. Поддерживаются ли `ref`, `in`, `out`, `ref struct` и `ref return`?
**Ответ:** Нет, они входят в официальный перечень неподдерживаемых элементов. Это особенно важно для высокопроизводительного кода и современных low-level API, которые не всегда совместимы с expression trees.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 66. Можно ли использовать interpolated strings напрямую?
**Ответ:** Нет, interpolated strings перечислены среди ограничений. В дереве обычно приходится представлять эквивалентную конкатенацию или вызовы форматирования, если провайдер вообще способен это обработать.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 67. Поддерживаются ли local functions?
**Ответ:** Нет, ссылки на local functions входят в список неподдерживаемых конструкций. Это еще один пример различия между общим синтаксисом C# и тем подмножеством, которое expression trees умеют отражать.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 68. Что с named arguments и optional arguments в вызовах методов?
**Ответ:** В списке ограничений указано, что method invocations с variable arguments, named arguments и optional arguments не поддерживаются. При проектировании API для LINQ-провайдеров это стоит учитывать заранее.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 69. Можно ли использовать range/index operators (`..`, `^`, `Index`, `Range`)?
**Ответ:** Нет, такие конструкции перечислены среди неподдерживаемых. Это важная деталь при переносе современного C#-кода в expression-driven DSL или ORM-запросы.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 70. Как practically обходить ограничения expression trees?
**Ответ:** Обычно есть три пути: переписать выражение в более старую форму, вынести часть логики из expression tree в обычный delegate после materialization, либо вручную собрать эквивалентное дерево через доступные узлы API. Выбор зависит от того, нужен ли анализ/трансляция или достаточно локального выполнения.[cite:1][cite:2]

**Ресурсы:** Expression Trees overview; Building Expression Trees.[cite:1][cite:2]

## 7. LINQ, IQueryable и провайдеры

### 71. Почему `IQueryable` связан с expression trees сильнее, чем `IEnumerable`?
**Ответ:** Потому что `IQueryable` строит и накапливает выражение запроса как дерево, которое затем передается провайдеру для интерпретации. `IEnumerable` же обычно работает с уже скомпилированными делегатами и выполняет их локально в памяти.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 72. Что происходит, когда вызывается `Queryable.Where`?
**Ответ:** На концептуальном уровне формируется новый узел вызова метода в дереве выражения, который описывает операцию фильтрации. Позже провайдер разбирает итоговую цепочку вызовов и строит собственный план выполнения.[cite:1][cite:6]

**Ресурсы:** Expression Trees overview; `System.Linq.Expressions` docs.[cite:1][cite:6]

### 73. Почему `Enumerable.Where` и `Queryable.Where` ведут себя по-разному?
**Ответ:** `Enumerable.Where` работает поверх делегатов и сразу выполняется над in-memory последовательностью, тогда как `Queryable.Where` принимает expression tree и откладывает реальное выполнение до тех пор, пока провайдер не интерпретирует запрос. Это фундаментальная разница между локальным вычислением и переводимым описанием запроса.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 74. Что значит “provider translates expression tree”?
**Ответ:** Это значит, что провайдер не вызывает ваш код как есть, а анализирует структуру дерева и преобразует ее в другую форму, например SQL, REST-фильтр или иной query language. Именно поэтому не все CLR-методы и конструкции можно использовать в `IQueryable`-запросах.[cite:1]

**Ресурсы:** Expression Trees overview.[cite:1]

### 75. Почему локальный пользовательский метод внутри `Where` часто не переводится?
**Ответ:** Потому что провайдер видит `MethodCallExpression`, но не обязан знать, как отобразить конкретный метод на SQL или другой backend. Если mapping не предусмотрен, запрос либо упадет, либо будет вынужден перейти к локальному выполнению, если это вообще допустимо.

**Ресурсы:** Expression Trees overview; Building Expression Trees.[cite:1][cite:2]

### 76. Что происходит, если слишком рано вызвать `ToList()` в LINQ-пайплайне?
**Ответ:** После materialization дальнейшие фильтры и проекции обычно переходят в LINQ to Objects и начинают работать уже с делегатами, а не с expression trees. Это меняет место выполнения, производительность и зачастую объем переданных данных.

**Ресурсы:** Expression Trees overview.[cite:1]

### 77. Почему expression trees позволяют строить динамические запросы?
**Ответ:** Потому что дерево можно собирать по частям во время выполнения, комбинируя узлы в зависимости от входных параметров пользователя. Документация Microsoft прямо отмечает, что building and running expression trees enables dynamic queries.[cite:1]

**Ресурсы:** Expression Trees overview; Building Expression Trees.[cite:1][cite:2]

### 78. Как объяснить difference between client-side and server-side evaluation через expression trees?
**Ответ:** Пока выражение остается в форме дерева и поддерживается провайдером, есть шанс выполнить его на сервере или целевой платформе. Как только часть логики компилируется в delegate или оказывается непереводимой, вычисление смещается на клиентскую сторону, что часто хуже по производительности и объему данных.

**Ресурсы:** Expression Trees overview; Executing Expression Trees.[cite:1][cite:9]

### 79. Почему предикат типа `Expression<Func<T,bool>>` лучше подходит для репозиториев, чем `Func<T,bool>`?
**Ответ:** Потому что репозиторий, работающий поверх `IQueryable`, может передать expression tree дальше в провайдер БД без потери структуры. С `Func<T,bool>` репозиторий вынужден фильтровать уже загруженные данные локально, если вообще может это сделать.[cite:1][cite:3]

**Ресурсы:** Expression Trees overview; `Expression<TDelegate>` API.[cite:1][cite:3]

### 80. Какой типовой interview trap связан с `AsEnumerable()`?
**Ответ:** Он переводит дальнейшую часть цепочки в LINQ to Objects, после чего `Queryable`-логика и translation semantics прекращаются. Если кандидат не замечает эту границу, он часто неверно рассуждает о месте выполнения и производительности.

**Ресурсы:** Expression Trees overview.[cite:1]

## 8. Комбинирование предикатов и динамические фильтры

### 81. Как динамически собрать `AND` из нескольких фильтров?
**Ответ:** Обычно стартуют с общего параметра `ParameterExpression`, строят отдельные булевы подвыражения и соединяют их через `Expression.AndAlso`. Ключевая деталь — все части должны использовать один и тот же объект параметра.

**Ресурсы:** Building Expression Trees.[cite:2]

### 82. Почему нельзя просто объединить два `Expression<Func<T,bool>>`, если у них разные параметры?
**Ответ:** Потому что даже если параметры имеют одинаковое имя и тип, это разные объекты `ParameterExpression`. Перед объединением один из предикатов нужно переписать так, чтобы оба ссылались на один и тот же параметр.

**Ресурсы:** Building Expression Trees; Interpret Expressions.[cite:2][cite:8]

### 83. Как обычно делают rebinding параметров при merge предикатов?
**Ответ:** Пишут visitor, который заменяет старый `ParameterExpression` на новый общий параметр. Это один из классических практических сценариев использования `ExpressionVisitor`.

**Ресурсы:** Interpret Expressions; `ExpressionVisitor.VisitAndConvert` API.[cite:8][cite:15]

### 84. Почему для логического объединения фильтров лучше `AndAlso`, а не `And`?
**Ответ:** `AndAlso` отражает привычную логическую семантику `&&` с коротким замыканием. Для предикатов и query translation именно это поведение обычно ожидается по смыслу.

**Ресурсы:** `System.Linq.Expressions` namespace docs.[cite:6]

### 85. Как построить фильтр по имени свойства, которое известно только строкой?
**Ответ:** Создают `ParameterExpression`, затем `Expression.Property` или эквивалентный member access по имени свойства, после чего строят нужное сравнение с `ConstantExpression`. Такой подход лежит в основе dynamic filtering и sorting UI-таблиц.

**Ресурсы:** Building Expression Trees; `System.Linq.Expressions` docs.[cite:2][cite:6]

### 86. Почему фильтры по строковым полям часто строят через `Expression.Call`?
**Ответ:** Потому что операции вроде `Contains`, `StartsWith` и `EndsWith` — это вызовы методов, а не бинарные операторы. Следовательно, в дереве они представлены как `MethodCallExpression`.[cite:2]

**Ресурсы:** Building Expression Trees.[cite:2]

### 87. Как правильно строить фильтр `x => list.Contains(x.Id)`?
**Ответ:** Нужно понимать, что это `MethodCallExpression`, где один операнд — коллекция значений, а другой — доступ к свойству. Для ORM такой шаблон часто переводится в `IN`, но только если провайдер умеет его распознать.

**Ресурсы:** Expression Trees overview; Building Expression Trees.[cite:1][cite:2]

### 88. Что делать, если значение фильтра приходит как string, а свойство — `int` или `DateTime`?
**Ответ:** Сначала нужно безопасно распарсить значение во внешний CLR-тип, а уже потом строить `ConstantExpression` нужного типа. Пытаться сравнивать несовместимые типы напрямую внутри дерева — частая причина runtime-ошибок.

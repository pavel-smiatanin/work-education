## 1. ООП: типы, значения и ссылки

### 1.1. В чём разница между value type и reference type?
Value type (struct, enum, встроенные числовые типы) хранит данные непосредственно в переменной — обычно на стеке или инлайново внутри объекта, содержащего его. При присваивании копируется всё значение. Reference type (class, interface, delegate, string, array) — переменная хранит ссылку (указатель) на объект в managed heap; при присваивании копируется только ссылка, оба имени указывают на один объект.

```csharp
struct Point { public int X, Y; }
class Box { public int Value; }

Point p1 = new Point { X = 1 };
Point p2 = p1;      // копия
p2.X = 99;           // p1.X всё ещё 1

Box b1 = new Box { Value = 1 };
Box b2 = b1;         // та же ссылка
b2.Value = 99;        // b1.Value тоже 99
```
Ресурсы: [Value types vs reference types — MS Learn](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/types/)

### 1.2. Где хранятся value types — всегда ли на стеке?
Нет, это частое заблуждение. Локальная value-переменная в методе действительно чаще всего лежит на стеке, но если она — поле класса (reference type) или элемент массива reference-типа, она хранится внутри объекта в heap. Также захваченные переменные в замыканиях и async-методах value types перемещаются компилятором в heap (в сгенерированный класс/структуру состояния).

```
Стек (пример вызова метода Foo)          Heap
┌───────────────┐                        ┌───────────────────┐
│ int x = 5      │                       │ MyClass instance    │
│ Point p (value) │                      │  int Field1          │
│ ref → obj ------┼----------------------▶  Point EmbeddedPoint │ ← value type внутри heap-объекта
└───────────────┘                        └───────────────────┘
```

### 1.3. Что такое boxing и unboxing, чем они опасны для производительности?
Boxing — неявное упаковывание value type в объект на heap (когда value type присваивается переменной типа `object` или интерфейса). Unboxing — обратное распаковывание с явным приведением типа. Каждая операция boxing создаёт новый объект в heap → нагрузка на GC, а частые boxing/unboxing в горячих путях (циклах, коллекциях `ArrayList`, non-generic коллекциях) заметно снижают производительность. Дженерики (`List<int>` вместо `ArrayList`) устраняют эту проблему.

### 1.4. В чём разница между `struct` и `class`?
`struct` — value type, не поддерживает наследование от других struct/class (только интерфейсы), не может иметь parameterless-конструктор до C# 10 (с C# 10 может), копируется по значению, не может быть null (если не `Nullable<T>` / `struct?`), обычно хранится компактнее и без GC-давления для коротких объектов. `class` — reference type, поддерживает наследование, всегда выделяется в heap, может быть null, передаётся по ссылке. Struct стоит использовать для маленьких неизменяемых наборов данных (координаты, деньги, DateTime).

### 1.5. Что такое readonly struct и зачем он нужен?
`readonly struct` гарантирует компилятору, что все поля структуры неизменяемы после конструктора. Это позволяет избежать неявного копирования при передаче `in`-параметров (compiler не должен создавать defensive copy на каждый вызов метода, т.к. знает, что структура не мутирует себя).
```csharp
readonly struct Money
{
    public readonly decimal Amount;
    public Money(decimal amount) => Amount = amount;
}
```

### 1.6. Чем `const` отличается от `readonly` и `static readonly`?
`const` — константа времени компиляции, значение встраивается (inline) в IL код во всех местах использования; требует примитивный/строковый тип и известное на этапе компиляции значение. `readonly` — поле, значение которого можно присвоить только в объявлении или конструкторе, вычисляется в runtime, можно использовать сложные типы. `static readonly` — то же самое, но общее для всех экземпляров класса. Важное следствие: если `const` объявлена в одной сборке, а используется в другой, при пересборке первой сборки без пересборки второй значение в потребителе останется старым (inline), а `static readonly` — всегда актуально.

### 1.7. Что такое immutability и почему она важна?
Неизменяемый (immutable) объект — тот, чьё состояние нельзя изменить после создания. Такие объекты по умолчанию потокобезопасны (нет гонок при чтении), их проще рассуждать (reasoning), они безопасны как ключи словарей/хэш-множеств. В C# для этого используют `readonly`-поля, `init`-свойства, records, `ImmutableList<T>` и подобные из `System.Collections.Immutable`.

### 1.8. Что такое `is` и `as`, чем отличаются от прямого приведения типов `(T)obj`?
`(T)obj` бросает `InvalidCastException`, если приведение невозможно. `obj as T` (только для reference types и Nullable<T>) возвращает `null` при неудачном приведении вместо исключения. `obj is T` возвращает `bool`, с C# 7 поддерживает pattern matching: `if (obj is T t) { ... }` — сразу объявляет типизированную переменную.

### 1.9. Что такое равенство ссылок vs равенство значений (`==`, `Equals`, `ReferenceEquals`)?
`ReferenceEquals(a, b)` всегда сравнивает ссылки (адреса). `Equals` по умолчанию (`Object.Equals`) тоже сравнивает ссылки для классов, но многие типы (string, record, value types через `ValueType.Equals`) переопределяют его для сравнения по значению. Оператор `==` для reference types по умолчанию — тоже ссылочное сравнение, но может быть переопределён (`operator ==`), как это сделано у `string`. Для value types `==` не определён автоматически (кроме встроенных числовых), нужно переопределять вручную либо использовать `record struct`.

### 1.10. Как правильно переопределять `Equals` и `GetHashCode`?
Нужно переопределять их согласованно: если `a.Equals(b) == true`, то `a.GetHashCode() == b.GetHashCode()` обязано быть true (обратное не обязательно). Нарушение контракта ломает работу `Dictionary<TKey,TValue>` и `HashSet<T>`. Рекомендуется также реализовать `IEquatable<T>` для типобезопасного сравнения без boxing и переопределить `operator ==`/`!=`.
```csharp
public override bool Equals(object obj) => obj is Point p && X == p.X && Y == p.Y;
public override int GetHashCode() => HashCode.Combine(X, Y);
```

### 1.11. Что такое `default(T)` и как он ведёт себя для value/reference типов?
Для reference types и nullable value types `default(T)` — это `null`. Для числовых value types — `0`/`0.0`. Для struct — экземпляр со всеми полями, равными их `default`. С C# 7.1 можно писать просто `default` без указания типа, если тип выводится из контекста.

### 1.12. Что такое partial class/method и зачем они нужны?
`partial class` позволяет разделить определение класса на несколько файлов — компилятор объединяет их в один тип при компиляции. Часто используется для генерируемого кода (Designer-файлы WinForms, EF миграции, source generators), чтобы не смешивать сгенерированный и ручной код. `partial method` — объявление метода без тела в одной части, с опциональной реализацией в другой; если реализация не предоставлена — вызовы такого метода полностью удаляются компилятором (zero overhead hook).

### 1.13. Чем `sealed` полезен, кроме запрета наследования?
Помимо явного запрета наследования (архитектурная защита инвариантов класса), `sealed` даёт понятную оптимизацию: JIT может девиртуализировать вызовы методов у sealed-класса (или методов, помеченных `sealed override`), заменяя виртуальный вызов на прямой, что быстрее.

### 1.14. В чём разница между `new` (сокрытие метода) и `override`?
`override` переопределяет виртуальный член — вызов через базовый или производный тип разрешается динамически (полиморфизм, via v-table). `new` скрывает член базового класса статически — какой метод вызовется, зависит от статического (объявленного) типа переменной, а не от реального типа объекта в runtime. Использование `new` вместо `override` — частая причина багов "неожиданного" поведения полиморфизма.

### 1.15. Что такое ковариантность и контравариантность (variance) в дженериках/делегатах?
Ковариантность (`out T`) позволяет использовать более производный тип там, где ожидается базовый (`IEnumerable<string>` можно передать как `IEnumerable<object>`). Контравариантность (`in T`) — наоборот, позволяет использовать более общий тип там, где ожидается конкретный (`Action<object>` можно использовать как `Action<string>`). Работает только для reference types и только в интерфейсах/делегатах с соответствующими модификаторами.

### 1.16. Что такое анонимные типы и record'ы — когда что использовать?
Анонимный тип (`new { Name = "A", Age = 1 }`) — компилятор генерирует immutable-класс "на лету", область видимости ограничена методом (либо LINQ-проекцией), нельзя передать как параметр метода по имени типа. `record` — именованный тип с value-based равенством, поддержкой `with`-выражений, пригоден как публичный DTO/контракт. Для внутренних временных проекций в LINQ обычно достаточно анонимных типов, для API-контрактов — record.

### 1.17. Что такое tuple (`ValueTuple`) и чем он отличается от `Tuple<T>`?
`Tuple<T1,T2,...>` — reference type (класс), выделяется в heap, поля называются `Item1`, `Item2`. `ValueTuple` (C# 7+, `(int, string)`) — struct, легковесный, поддерживает именованные элементы (`(int Id, string Name)`), удобен для возврата нескольких значений из метода без создания отдельного класса.

### 1.18. Что такое deconstruction (деконструкция) в C#?
Механизм разложения объекта на составляющие через метод `Deconstruct`. Встроенно поддерживается у tuple и records, можно реализовать для любого типа.
```csharp
var (id, name) = GetUser();  // requires void Deconstruct(out int id, out string name)
```

### 1.19. Что такое extension methods и какие у них ограничения?
Статические методы в статическом классе с модификатором `this` у первого параметра, позволяющие «расширять» существующий тип без изменения его исходного кода и без наследования. Ограничения: нет доступа к private/protected членам расширяемого типа, не участвуют в полиморфизме (разрешение — статическое, по типу времени компиляции), метод экземпляра с тем же именем всегда имеет приоритет над extension-методом.

### 1.20. Что такое indexers (`this[]`) и когда их стоит использовать?
Indexer позволяет обращаться к объекту как к массиву: `obj[key]`. Полезен для классов-коллекций/оберток над данными (свои реализации словарей, матриц, конфигураций). Может иметь несколько перегрузок с разными типами параметров и быть доступным только для чтения/записи.

## 2. ООП: наследование, полиморфизм, интерфейсы

### 2.1. В чём разница между абстрактным классом и интерфейсом?
Абстрактный класс может содержать реализованные и абстрактные члены, поля, конструкторы, модификаторы доступа; поддерживает только одиночное наследование. Интерфейс до C# 8 мог содержать только сигнатуры (без реализации); начиная с C# 8 поддерживает default-реализации методов, но по-прежнему не может иметь состояние (instance-поля) и поддерживает множественную реализацию. Выбор: абстрактный класс — для "is-a" отношения с общей реализацией и состоянием; интерфейс — для контракта поведения ("can-do"), особенно при множественной реализации.

### 2.2. Что такое default interface methods (C# 8) и какие проблемы они решают?
Позволяют добавлять реализацию по умолчанию прямо в интерфейс, чтобы можно было расширять публичный интерфейс новыми членами, не ломая существующие реализации (versioning API без breaking change). Классический пример из .NET — расширение `IEnumerable` подобных интерфейсов в библиотеках без принудительного обновления всех реализаций.

### 2.3. Как работает виртуальный вызов методов на уровне CLR (v-table)?
Каждый тип с виртуальными методами имеет таблицу методов (method table); экземпляр объекта хранит указатель на неё. При вызове `virtual`/`override` метода CLR ищет в v-table фактического типа объекта (а не статического типа переменной) нужный слот и вызывает реализацию оттуда — это и обеспечивает полиморфизм. Невиртуальные методы разрешаются статически на этапе компиляции (или JIT), без обращения к v-table.

```
Base v-table            Derived v-table
┌───────────────┐       ┌───────────────┐
│ 0: Method A    │       │ 0: Method A (override) │
│ 1: Method B    │       │ 1: Method B (унаследован)│
└───────────────┘       └───────────────┘
        obj (Derived) → указывает на Derived v-table
```

### 2.4. Можно ли вызвать виртуальный метод из конструктора? Почему это плохая практика?
Технически можно, но опасно: если конструктор базового класса вызывает виртуальный метод, а он переопределён в производном классе, то на момент вызова конструктор производного класса ещё не отработал — поля производного класса могут быть неинициализированы (значения по умолчанию), что приводит к трудноуловимым багам.

### 2.5. Что такое abstract, virtual, override, new, sealed override — сравнение модификаторов.
`abstract` — член без реализации, обязателен к переопределению в неабстрактном наследнике. `virtual` — член с реализацией, может быть переопределён. `override` — переопределяет virtual/abstract член родителя. `new` — скрывает член родителя без полиморфизма. `sealed override` — переопределяет метод и запрещает дальнейшее переопределение в более глубоких наследниках (при этом позволяет JIT девиртуализацию).

### 2.6. Явная и неявная реализация интерфейса (explicit interface implementation) — зачем нужна явная?
Неявная реализация — метод интерфейса становится публичным членом класса. Явная (`void IFoo.Bar()`) — метод доступен только через приведение к интерфейсу, не отображается в публичном API класса напрямую. Используется, когда: два интерфейса объявляют метод с одинаковой сигнатурой, но разной семантикой; нужно скрыть техническую реализацию контракта от основного API класса.

### 2.7. Как работает множественное наследование интерфейсов при конфликте default-реализаций?
Если класс реализует два интерфейса с одинаковым default-методом, компилятор требует явно переопределить метод в классе (diamond problem решается принудительным разрешением конфликта разработчиком, а не автоматическим слиянием).

### 2.8. Что такое композиция vs наследование, и почему "favor composition over inheritance"?
Наследование создаёт жёсткую связь is-a и раскрывает внутреннюю реализацию базового класса наследникам (нарушение инкапсуляции, "хрупкий базовый класс"). Композиция ("has-a") — объект содержит ссылки на другие объекты и делегирует им работу, что даёт гибкость (можно менять поведение в runtime, легче тестировать через подмену зависимостей) и меньшую связанность. Общее правило: наследование — для истинной таксономии типов и полиморфизма, композиция — для переиспользования поведения.

### 2.9. Что такое протected internal и private protected?
`protected internal` — доступ разрешён производным классам ИЛИ коду в той же сборке (объединение через ИЛИ). `private protected` (C# 7.2) — доступ разрешён только производным классам, которые至 находятся в той же сборке (пересечение через И). Это самый узкий составной модификатор доступа.

### 2.10. Как работает порядок инициализации при создании объекта (поля, конструкторы базового и производного класса)?
Порядок: 1) статические поля/конструктор типа (один раз, при первом обращении к типу); 2) инстанс-поля базового класса инициализируются их inline-инициализаторами; 3) выполняется тело конструктора базового класса; 4) инстанс-поля производного класса инициализируются; 5) выполняется тело конструктора производного класса. Именно поэтому вызов виртуального метода из базового конструктора небезопасен (см. 2.4).

### 2.11. Что такое инкапсуляция и как модификаторы доступа её обеспечивают?
Инкапсуляция — сокрытие внутреннего состояния объекта и предоставление контролируемого доступа через public-методы/свойства. Модификаторы `private`, `protected`, `internal`, `public`, `protected internal`, `private protected` задают границы видимости членов, позволяя защищать инварианты класса от некорректного внешнего изменения.

### 2.12. Чем `IComparable<T>` отличается от `IComparer<T>`?
`IComparable<T>` реализуется самим типом — определяет "естественный" порядок сортировки объекта (`CompareTo`). `IComparer<T>` — отдельный внешний объект-компаратор, позволяющий задать альтернативный порядок сортировки без изменения самого типа (например, `List<T>.Sort(IComparer<T>)`, разные сортировки для одного и того же класса).

### 2.13. Что такое `IDisposable` и когда стоит его реализовывать в собственном классе?
Интерфейс с методом `Dispose()` для детерминированного освобождения неуправляемых ресурсов (файлы, сокеты, БД-соединения, unmanaged handles) сразу, не дожидаясь GC. Реализуется, если класс напрямую или через поля владеет unmanaged-ресурсами или другими IDisposable-объектами. Используется вместе с `using`/`using var`.

### 2.14. Как правильно реализовать Dispose Pattern с финализатором?
```csharp
public class Resource : IDisposable
{
    private bool _disposed;
    private IntPtr _handle; // unmanaged
    private SafeHandle _safeHandle; // managed wrapper

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        if (disposing)
        {
            _safeHandle?.Dispose(); // managed resources
        }
        // освободить unmanaged resources напрямую, если есть
        _disposed = true;
    }

    ~Resource() => Dispose(false);
}
```
Финализатор — подстраховка на случай, если потребитель забыл вызвать `Dispose()`; `GC.SuppressFinalize` отменяет вызов финализатора, если Dispose уже отработал (экономит проход GC).

### 2.15. Что такое интерфейс-маркер (marker interface) и есть ли им замена в современном C#?
Интерфейс без членов, используемый только для пометки типа метаданными (например, исторически `ISerializable`-подобные маркеры). Современная альтернатива — атрибуты (`[Attribute]`), которые несут метаданные без обязательства реализовывать какие-либо методы и проверяются через рефлексию.

### 2.16. Как устроено множественное наследование через интерфейсы и явную реализацию при коллизии имён?
Если класс реализует два интерфейса с методами одинаковой сигнатуры, но с разной ожидаемой семантикой, можно реализовать оба метода явно (`void IA.Foo()`, `void IB.Foo()`), тогда вызов зависит от того, к какому интерфейсу приведена переменная — так снимается неоднозначность без единственной "объединённой" реализации.

### 2.17. Что такое паттерн Template Method и как его выразить через abstract class?
Базовый класс определяет "скелет" алгоритма в неабстрактном методе, вызывающем один или несколько abstract/virtual "шагов", которые переопределяют наследники — так фиксируется общая структура процесса при вариативности отдельных шагов.
```csharp
abstract class ReportGenerator
{
    public void Generate() { FetchData(); FormatData(); Save(); }
    protected abstract void FetchData();
    protected virtual void FormatData() { /* default */ }
    protected abstract void Save();
}
```

### 2.18. Чем отличается "is-a" от "has-a" и как это влияет на выбор структуры класса?
"is-a" — отношение специализации (Dog is-a Animal) — кандидат на наследование. "has-a" — отношение владения/использования (Car has-a Engine) — кандидат на композицию (поле-ссылку на другой объект). Неправильный выбор (наследование там, где нужна композиция) — частый источник негибкой архитектуры.

### 2.19. Что такое record class vs record struct и как выбрать между ними для DTO?
`record class` (по умолчанию `record`) — reference type с value-equality и `with`-expressions. `record struct` (C# 10) — value type с той же семантикой value-equality. Для маленьких неизменяемых DTO, часто копируемых по значению (координаты, деньги) — предпочтительнее `record struct`, чтобы избежать лишних heap-аллокаций; для более крупных доменных объектов, передаваемых по ссылке — `record class`.

### 2.20. Как работает разрешение перегрузок (overload resolution) при неоднозначности?
Компилятор выбирает наиболее конкретную применимую перегрузку по правилам: точное совпадение типов > расширяющее преобразование (implicit numeric conversion) > boxing > params-массив как последний вариант. Если две перегрузки одинаково "лучше" по этим правилам и ни одна не доминирует над другой — компилятор выдаёт ошибку неоднозначности (ambiguous call), а не выбирает случайную.

## 3. Управление памятью и Garbage Collector

### 3.1. Как устроен managed heap и generational GC в .NET?
GC делит heap на поколения: Gen0 (молодые, часто умирающие объекты), Gen1 (буфер между Gen0 и Gen2), Gen2 (долгоживущие объекты) и отдельно Large Object Heap (LOH, объекты ≥85 000 байт). Сборка Gen0 происходит часто и быстро, Gen2 — редко и дороже. Объект, переживший сборку своего поколения, "повышается" (promotion) в следующее — это основано на "generational hypothesis": большинство объектов умирают молодыми.

```
Gen0 (частая сборка) → выжившие → Gen1 (буфер) → выжившие → Gen2 (редкая, полная сборка)
                                                      ↑
                                     LOH (крупные объекты, ≥ 85000 байт, собирается вместе с Gen2)
```

### 3.2. Что такое mark-and-sweep и compacting в контексте .NET GC?
GC сначала помечает (mark) все объекты, достижимые из корней (стек, статические поля, регистры, GC-handles) — это "живые" объекты, недостижимые считаются мусором. Затем "compacting"-фаза сдвигает выжившие объекты вместе, чтобы устранить фрагментацию и получить непрерывное свободное пространство (кроме LOH, который по умолчанию не компактируется, что может вызвать фрагментацию — можно принудительно включить `GCSettings.LargeObjectHeapCompactionMode`).

### 3.3. Что такое GC roots?
Корни — отправные точки, с которых GC начинает обход графа объектов: локальные переменные и параметры в стеке активных методов, статические поля, CPU-регистры, GC handles (например, из unmanaged-кода). Всё, что недостижимо ни из одного корня — кандидат на сборку.

### 3.4. В чём разница между Workstation GC и Server GC?
Workstation GC оптимизирован для клиентских приложений с одним основным потоком-исполнителем, минимизирует паузы. Server GC создаёт по heap и потоку сборки на каждое ядро CPU, оптимизирован под высокую пропускную способность на серверах с многими ядрами (используется по умолчанию в ASP.NET Core). Настраивается через `<ServerGarbageCollection>` в csproj или `runtimeconfig.json`.

### 3.5. Что такое Large Object Heap (LOH) и его особенности?
Объекты ≥85 000 байт (обычно большие массивы) размещаются в LOH. LOH собирается вместе с Gen2 (дорогая операция) и по умолчанию не компактируется — множественные аллокации/освобождения больших объектов приводят к фрагментации памяти. Способы борьбы: переиспользование буферов через `ArrayPool<T>`, включение LOH-компактации при необходимости.

### 3.6. Что такое финализатор (`~ClassName`) и почему его следует избегать без необходимости?
Финализатор вызывается GC перед освобождением памяти объекта для очистки unmanaged-ресурсов. Объекты с финализатором переживают минимум одну дополнительную сборку — сначала помещаются в очередь финализации (freachable queue) и собираются только на следующем цикле после выполнения финализатора отдельным потоком, что увеличивает время жизни объекта и нагрузку на GC. Предпочтительно использовать `SafeHandle`/`IDisposable` вместо явного финализатора.

### 3.7. Что такое weak reference (`WeakReference<T>`) и когда её использовать?
Слабая ссылка позволяет ссылаться на объект, не препятствуя его сборке GC (объект может быть собран, даже если на него есть weak reference). Полезна для кэшей, где элементы можно пересоздать при необходимости, и не нужно, чтобы кэш препятствовал освобождению памяти.
```csharp
var wr = new WeakReference<MyObject>(obj);
if (wr.TryGetTarget(out var target)) { /* объект ещё жив */ }
```

### 3.8. Что такое memory leak в managed-коде — как он вообще возможен при наличии GC?
Утечка происходит, когда объект остаётся достижимым (есть живая ссылка на него из корня), хотя логически он больше не нужен — GC не может его собрать. Частые причины: неотписанные обработчики событий (event handler держит подписчика живым через ссылку на делегат), статические коллекции/кэши без ограничения размера, захваченные ссылки в замыканиях, незакрытые `IDisposable`.

### 3.9. Почему подписка на событие без отписки — частая причина утечек?
Издатель события хранит список делегатов-подписчиков. Пока издатель жив (например, статический или долгоживущий объект), подписчик остаётся достижимым через этот делегат, даже если сам подписчик больше нигде не используется — GC не может его собрать. Решения: явная отписка (`-=`), `WeakEventManager`, слабые события, или паттерн IDisposable для отписки при уничтожении подписчика.

### 3.10. Что такое `GC.Collect()` и почему его почти никогда не стоит вызывать вручную?
Принудительно запускает сборку мусора. Практически всегда GC сам выбирает оптимальный момент для сборки на основе эвристик; ручной вызов нарушает эти эвристики, может вызвать полную блокирующую Gen2-сборку там, где она не нужна, и снизить производительность. Оправданные случаи крайне редки (например, сразу после разового пикового потребления памяти в consоль-утилите перед долгим простоем).

### 3.11. Что такое `IDisposable` + `using`/`using var` и как компилятор это транслирует?
`using` разворачивается компилятором в `try/finally`, где `Dispose()` вызывается в блоке `finally` — гарантируя освобождение ресурса даже при исключении. `using var x = ...;` (C# 8) — "declaration"-форма, Dispose вызывается в конце содержащего блока (метода), без явной вложенности.

### 3.12. Что такое `Span<T>` и как он помогает снизить давление на GC?
`Span<T>` — ref struct, представляющий непрерывный участок памяти (массив, часть массива, стековую память, unmanaged-память) без копирования данных и без выделения в heap. Позволяет писать код, работающий со срезами данных (парсинг строк, буферов) без лишних аллокаций подмассивов/подстрок. Ограничение: как `ref struct`, `Span<T>` нельзя хранить в полях класса, использовать в async-методах или боксить, так как он должен жить только на стеке.

### 3.13. Как GC отслеживает поколения при мутации ссылок (write barrier, card table)?
Когда объект из Gen2 получает ссылку на объект из Gen0 (например, через поле), GC должен знать об этом при сборке Gen0, не сканируя весь Gen2. Для этого CLR использует write barrier — код, срабатывающий при каждой записи ссылочного поля, который отмечает соответствующую "карту" (card table); при Gen0-сборке GC сканирует только помеченные карты, а не весь Gen2 — так поддерживается эффективность частых молодых сборок.

### 3.14. Чем отличается `Dispose()` от финализатора с точки зрения детерминированности?
`Dispose()` вызывается явно и детерминированно (сразу, когда вызван, или в конце `using`-блока). Финализатор вызывается GC недетерминированно — в какой-то момент после того, как объект стал недостижим, время неизвестно заранее и не гарантируется вовсе (например, при аварийном завершении процесса). Поэтому критичные к таймингу ресурсы (файловые дескрипторы, соединения) следует освобождать через `Dispose`, а не полагаться на финализатор.

### 3.15. Что такое `stackalloc` и когда он оправдан?
Выделяет блок памяти прямо на стеке текущего метода (а не в heap), доступ через `Span<T>`. Память автоматически освобождается при выходе из метода, без участия GC. Используется для небольших временных буферов в горячих путях кода (парсинг, криптография), где важно избежать heap-аллокаций. Требует осторожности с размером (риск переполнения стека) и `unsafe`/безопасного `Span`-обёртывания.

### 3.16. Что такое `GCSettings.LatencyMode` и `SustainedLowLatency`?
Позволяет настроить поведение GC в пользу меньших пауз ценой большего потребления памяти — полезно для приложений, чувствительных к задержкам (аудио/видео, торговые системы), где недопустимы долгие Gen2-паузы в критичных участках выполнения.

### 3.17. В чём разница между управляемой (managed) и неуправляемой (unmanaged) памятью в контексте .NET?
Managed-память управляется CLR и GC — выделение/освобождение автоматическое. Unmanaged-память (например, полученная через `Marshal.AllocHGlobal`, дескрипторы ОС, память из P/Invoke) GC "не видит" и не освобождает — ответственность за освобождение лежит на разработчике (обычно через `SafeHandle` или явный `Dispose`/`Marshal.FreeHGlobal`).

### 3.18. Что произойдёт, если исключение выбросится внутри `Dispose()`?
Оно распространится как обычное исключение. Если `Dispose()` вызывается в `finally`-блоке (например, сгенерированном из `using`) при уже активном исключении из `try`-блока, новое исключение из `Dispose` заменит собой исходное (если не обёрнуто в `AggregateException` вручную) — оригинальная причина сбоя может потеряться. Поэтому `Dispose()` рекомендуется писать так, чтобы он не бросал исключений (best practice, аналог `noexcept`).

## 4. Делегаты, события, лямбда-выражения

### 4.1. Что такое делегат и как он устроен внутри?
Делегат — типобезопасный указатель на один или несколько методов с определённой сигнатурой. Внутри это класс (генерируется компилятором), наследующий `MulticastDelegate`, хранящий список пар (target-объект, указатель на метод) — invocation list. Вызов делегата последовательно вызывает все методы из списка.

### 4.2. Чем `Func<T>`, `Action<T>` и `Predicate<T>` отличаются друг от друга?
`Action<T...>` — делегат без возвращаемого значения (void). `Func<T..., TResult>` — делегат, возвращающий значение (последний параметр типа — тип результата). `Predicate<T>` — частный случай `Func<T,bool>`, семантически означает "условие/фильтр", используется, например, в `List<T>.Find(Predicate<T>)`.

### 4.3. Что такое multicast delegate и в каком порядке вызываются подписчики?
Делегат может ссылаться на несколько методов одновременно (через `+=`), формируя invocation list. При вызове методы выполняются последовательно в порядке добавления. Если делегат возвращает значение — вызывающий код получит только результат последнего вызванного метода в цепочке, промежуточные результаты теряются (если не собирать их вручную через `GetInvocationList()`).

### 4.4. Как правильно и безопасно отписываться от событий?
Всегда парой к подписке: `obj.Event += Handler;` ... `obj.Event -= Handler;`, обычно в `Dispose()`/деструкторе подписчика или при завершении его жизненного цикла. Для анонимных лямбда-подписчиков без сохранённой ссылки отписаться невозможно — если нужна отписка, лямбду нужно сохранить в переменную/поле.

### 4.5. Чем `event` отличается от простого публичного поля-делегата?
`public event Action MyEvent;` ограничивает внешний доступ — извне можно только `+=`/`-=`, но нельзя вызвать событие (`MyEvent()`) или присвоить (`=`), заменив весь invocation list — это может делать только сам класс-издатель. Простое публичное поле делегата (`public Action MyEvent;`) не имеет таких ограничений — извне можно перезаписать весь список подписчиков или вызвать напрямую, что нарушает инкапсуляцию.

### 4.6. Что такое замыкание (closure) и какие с ним связаны подводные камни?
Замыкание — лямбда/анонимный метод, "захватывающий" внешние переменные по ссылке (а не по значению), продлевая их время жизни до времени жизни делегата. Классическая ловушка — захват переменной цикла:
```csharp
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
    actions.Add(() => Console.WriteLine(i));
// C# 5+: for создаёт новую переменную i на каждой итерации → выведет 0,1,2
// НО foreach var в C# < 5 захватывал одну и ту же переменную — печатал 3,3,3 (исправлено в C# 5)
```
С C# 5 семантика `for`/`foreach` изменена так, что каждая итерация имеет собственный экземпляр переменной цикла, что устранило самую частую ловушку.

### 4.7. Как делегаты связаны с событиями GC/утечками памяти (см. также 3.9)?
Делегат хранит ссылку на target-объект. Подписка долгоживущего издателя на метод короткоживущего подписчика удерживает подписчика в памяти дольше, чем ожидается, если не отписаться — это одна из самых частых причин managed memory leaks в .NET.

### 4.8. Что такое лямбда-выражения и expression trees, чем они отличаются?
Лямбда, присвоенная делегату (`Func<int,int> f = x => x*2;`), компилируется в обычный IL-метод. Та же лямбда, присвоенная `Expression<Func<int,int>>`, компилируется в дерево выражений (Expression Tree) — структуру данных, описывающую код декларативно, которую можно анализировать и транслировать в runtime (это основа LINQ to SQL/EF Core, которые превращают C#-выражения в SQL).

### 4.9. Как работает `EventHandler` и `EventHandler<TEventArgs>` — стандартный паттерн событий в .NET?
Соглашение .NET: `public event EventHandler<MyEventArgs> Something;`, сигнатура `void Handler(object sender, TEventArgs e)`. `sender` — источник события (полезно, когда один обработчик подписан на несколько источников), `TEventArgs` — наследник `EventArgs`, несущий данные о событии. Это унифицированный контракт, ожидаемый многими инструментами и разработчиками.

### 4.10. Что такое `Func<>`/делегаты как стратегия внедрения поведения (Strategy pattern через делегаты)?
Вместо создания иерархии классов-стратегий с интерфейсом можно передавать поведение напрямую как делегат (`Func<T,bool>` фильтр, `Comparison<T>` компаратор) — легковесная альтернатива паттерну Strategy для простых случаев, где не нужно состояние или множество связанных методов.

### 4.11. Чем `Action`/`Func` отличаются от объявления собственного `delegate`-типа?
Функционально идентичны — `Func`/`Action` это просто общецелевые generic-делегаты из BCL. Собственный именованный `delegate` (`delegate bool Validator(string s);`) полезен, когда сигнатура несёт смысловую нагрузку в имени типа, для параметров `out`/`ref` (которые `Func`/`Action` не поддерживают), либо для публичного API, где явное имя типа улучшает читаемость.

### 4.12. Как делегаты используются для реализации паттерна "Callback"?
Метод принимает делегат как параметр и вызывает его в определённый момент выполнения (например, по завершении асинхронной операции или на каждой итерации). Это основа многих API до эры `async/await` (`BeginInvoke`/`AsyncCallback`) и остаётся полезным паттерном для хуков расширения поведения.

### 4.13. Что такое `Comparison<T>` и как он используется в `List<T>.Sort`?
Делегат `int Comparison<T>(T x, T y)`, аналог `IComparer<T>.Compare`, но без обёртки в интерфейс — удобен, когда нужно передать сортировку "на лету" лямбдой: `list.Sort((a, b) => a.Age.CompareTo(b.Age));`.

### 4.14. Могут ли делегаты указывать на статические и на методы экземпляра одновременно в одном invocation list?
Да, invocation list может содержать смесь ссылок на статические методы (target = null) и методы экземпляра (target = конкретный объект) — делегат не делает различий, кроме внутреннего хранения ссылки на target для методов экземпляра.

### 4.15. Что такое `+=`/`-=` на уровне компиляции для event — это потокобезопасно?
Компилятор превращает `event1 += handler` в вызов `Delegate.Combine`, а `-=` — в `Delegate.Remove`. Сами по себе делегаты immutable (Combine/Remove создают новый делегат, а не мутируют старый), но не гарантируется atomic-присвоение полю без явной синхронизации в многопоточном сценарии — начиная с .NET, автогенерируемые event accessor'ы используют `Interlocked.CompareExchange` под капотом (с C# компиляторов последних версий) для потокобезопасного добавления/удаления обработчиков по умолчанию.

## 5. LINQ

### 5.1. В чём разница между отложенным (deferred) и немедленным (immediate) выполнением LINQ-запросов?
Большинство LINQ-операторов (`Where`, `Select`, `OrderBy`...) откладывают выполнение до момента фактического перечисления результата (`foreach`, `ToList()`, `.First()`) — запрос описывает "что делать", а не выполняется сразу. Операторы вроде `ToList()`, `ToArray()`, `Count()`, `Sum()` выполняют запрос немедленно и материализуют результат. Следствие: если источник данных изменится между определением и перечислением отложенного запроса, результат будет отражать актуальное состояние на момент перечисления.

### 5.2. Чем `IEnumerable<T>` отличается от `IQueryable<T>`?
`IEnumerable<T>` выполняет операции в памяти (LINQ to Objects) — каждый оператор транслируется в обычный C#-код/делегаты. `IQueryable<T>` строит Expression Tree и откладывает исполнение до провайдера (например, EF Core), который транслирует всё дерево выражений в SQL и выполняет запрос на стороне БД — важно фильтровать/агрегировать через `IQueryable` до вызова `.ToList()`, иначе можно случайно выгрузить всю таблицу в память и фильтровать её уже в LINQ to Objects.

### 5.3. Что произойдёт при "N+1 запросы" (N+1 problem) через LINQ to Entities и как их избежать?
Проблема: код обращается к навигационному свойству внутри цикла по коллекции без явной загрузки (`.Include`), из-за чего ORM выполняет по одному дополнительному SQL-запросу на каждый элемент вместо одного JOIN-запроса. Решение — явная загрузка (`Include`/`ThenInclude` в EF Core), проекция нужных данных сразу в исходном запросе, либо batch-загрузка.

### 5.4. Чем `Select` отличается от `SelectMany`?
`Select` проецирует каждый элемент в новый элемент (1-к-1, результат — `IEnumerable<TResult>` той же "формы" последовательности). `SelectMany` проецирует каждый элемент в последовательность и "разворачивает" (flatten) все получившиеся последовательности в одну общую — используется для работы с коллекциями коллекций (например, все заказы всех клиентов одним плоским списком).

### 5.5. В чём разница между `First`, `FirstOrDefault`, `Single`, `SingleOrDefault`?
`First` — бросает исключение, если последовательность пуста; возвращает первый элемент. `FirstOrDefault` — возвращает `default(T)` вместо исключения при пустой последовательности. `Single` — требует РОВНО один элемент, бросает исключение и при пустой последовательности, и при более чем одном элементе. `SingleOrDefault` — `default(T)` при пустой, исключение при более чем одном.

### 5.6. Как правильно использовать `GroupBy`, что возвращает результат?
`GroupBy` возвращает `IEnumerable<IGrouping<TKey,TElement>>` — последовательность групп, каждая группа сама является последовательностью элементов с общим ключом (`group.Key`). При использовании с `IQueryable`/EF Core важно учитывать, что не все виды группировки хорошо транслируются в SQL — сложную группировку иногда эффективнее выполнять после материализации в памяти.

### 5.7. Чем `Join` отличается от `GroupJoin` в LINQ?
`Join` — аналог inner join в SQL, для каждой пары совпадающих ключей создаёт одну строку результата (плоское соединение). `GroupJoin` — аналог left outer join с группировкой: для каждого элемента внешней последовательности собирает коллекцию всех совпадающих элементов внутренней последовательности (даже пустую), результат — по одной записи на каждый элемент внешней последовательности с вложенной коллекцией.

### 5.8. Как работает `Aggregate` и когда он полезен вместо `Sum`/встроенных агрегатов?
`Aggregate` — универсальная свёртка последовательности с накопителем и пользовательской функцией комбинирования, полезна, когда нужной агрегатной функции нет из коробки (например, конкатенация строк с разделителем, произведение элементов, сложная бизнес-логика свёртки).
```csharp
int product = numbers.Aggregate(1, (acc, x) => acc * x);
```

### 5.9. Почему множественное перечисление одного и того же `IEnumerable<T>` может быть проблемой производительности?
Из-за отложенного выполнения каждое новое перечисление (`foreach`, повторный `.Count()` и `.ToList()` на одном объекте `IEnumerable`) заново выполняет всю цепочку операторов от источника — если источник дорогой (запрос к БД, чтение файла) или запрос содержит побочные эффекты, это приводит к повторным дорогим вычислениям и потенциально разным результатам между вызовами. Решение — материализовать результат один раз (`.ToList()`/`.ToArray()`), если он используется многократно.

### 5.10. В чём разница между `OrderBy().ThenBy()` и несколько раз `OrderBy()` подряд?
`ThenBy` добавляет вторичный критерий сортировки, сохраняя первичный (стабильная многоуровневая сортировка). Повторный вызов `OrderBy` после уже отсортированной последовательности игнорирует предыдущую сортировку и пересортировывает по новому ключу как по первичному — предыдущий порядок теряется (это частая ошибка вместо `ThenBy`).

### 5.11. Что такое `Distinct`, `DistinctBy` (.NET 6+), и как задать собственный критерий сравнения?
`Distinct()` убирает дубликаты, используя `IEqualityComparer<T>` (по умолчанию `EqualityComparer<T>.Default`, то есть `Equals`/`GetHashCode`). Можно передать свой `IEqualityComparer<T>`. `DistinctBy(keySelector)` (начиная с .NET 6) убирает дубликаты по значению, вычисленному через селектор, без необходимости писать отдельный компаратор для всего объекта.

### 5.12. Как работает `Any()` vs `Count() > 0` с точки зрения производительности?
`Any()` останавливается на первом найденном элементе (или сразу возвращает false для пустой коллекции) — O(1) в лучшем случае для перечисления. `Count()` для `IEnumerable<T>` (без быстрого пути `ICollection.Count`) вынужден перечислить всю последовательность, чтобы посчитать общее число элементов — то есть `Count() > 0` может быть значительно дороже `Any()` на больших/дорогих последовательностях.

### 5.13. Чем query syntax (`from x in ...`) отличается от method syntax (`.Where(...)`) — есть ли разница в производительности?
Query syntax — синтаксический сахар, компилятор транслирует его в идентичные вызовы методов расширения (method syntax) на этапе компиляции — разницы в производительности нет, это чисто стилистический выбор. Некоторые операторы (например, `let`, множественные `join`) выразительнее в query syntax, другие (`Skip`, `Take`, `Distinct`) есть только в method syntax.

### 5.14. Как транслируется LINQ-запрос к `IQueryable` в SQL — какова роль `Expression<TDelegate>`?
Провайдер (например, EF Core) не выполняет ваш C#-код напрямую — он анализирует Expression Tree, построенное из лямбда-выражений вашего запроса, и переводит его в SQL-эквивалент. Поэтому в `IQueryable`-запросах нельзя использовать произвольные C#-методы без специальной поддержки провайдера (LINQ to Objects такого ограничения не имеет, так как выполняется как обычный managed-код).

### 5.15. Что такое `Zip` и `Chunk` (.NET 6+)?
`Zip` объединяет два (или три) параллельных последовательности поэлементно в кортежи/результат, останавливаясь на самой короткой. `Chunk(size)` (.NET 6+) разбивает последовательность на массивы фиксированного максимального размера — удобно для батчевой обработки большого набора данных.

### 5.16. Как работает `ToDictionary`/`ToLookup`, чем `Lookup` отличается от `Dictionary`?
`ToDictionary(keySelector)` требует уникальности ключей, иначе бросает исключение. `ToLookup(keySelector)` строит структуру, аналогичную `Dictionary<TKey, IEnumerable<TElement>>`, но допускает дублирующиеся ключи (группирует значения) и, в отличие от `GroupBy`, вычисляется немедленно (eager), а не отложенно.

### 5.17. Что такое custom LINQ operator и как его написать через extension methods + `yield return`?
Можно расширить LINQ собственными операторами, написав generic extension-метод над `IEnumerable<T>`, использующий `yield return` для ленивой генерации результата — это позволяет писать собственные оптимизированные/специализированные операторы, органично встраивающиеся в LINQ-цепочку.
```csharp
public static IEnumerable<T> WhereNotNull<T>(this IEnumerable<T?> source) where T : class
{
    foreach (var item in source)
        if (item is not null) yield return item;
}
```

### 5.18. Как устроен `yield return` и итераторы под капотом — что генерирует компилятор?
Метод с `yield return` компилятор превращает в отдельный класс — конечный автомат (state machine), реализующий `IEnumerator<T>`/`IEnumerable<T>`, который сохраняет "точку выполнения" между вызовами `MoveNext()`. Код метода фактически не выполняется целиком сразу — каждый `MoveNext()` продолжает выполнение с того места, где был предыдущий `yield return`, что и обеспечивает ленивую (отложенную) генерацию последовательности.

## 6. Асинхронность и многопоточность

### 6.1. В чём принципиальная разница между многопоточностью (multithreading) и асинхронностью (async)?
Многопоточность — выполнение нескольких потоков параллельно (используя несколько ядер CPU) для CPU-bound задач. Асинхронность — способ не блокировать текущий поток во время ожидания I/O-bound операции (сеть, диск, БД) — поток освобождается на время ожидания и может выполнять другую работу, не требуя дополнительных потоков "в простое". `async/await` сам по себе не создаёт новых потоков — это про эффективное использование существующих.

### 6.2. Как устроен `async/await` под капотом — что генерирует компилятор?
Метод с `async` компилятор превращает в конечный автомат (state machine, обычно struct, реализующий `IAsyncStateMachine`), где каждый `await` — точка, в которой выполнение может приостановиться, вернув управление вызывающему коду (через `Task`, представляющий будущее завершение), и возобновиться позже (через continuation), когда awaited-операция завершится — без блокировки потока на время ожидания.

```
Task DoAsync()
{
  var sm = new <DoAsync>d__0 { state = -1 };
  sm.MoveNext(); // запускает выполнение до первого await
  return sm.Builder.Task; // Task возвращается сразу
}
// внутри MoveNext(): switch(state) { case 0: ... await продолжение ... }
```

### 6.3. Что такое `SynchronizationContext` и почему важно понимать `ConfigureAwait(false)`?
`SynchronizationContext` определяет, куда должно вернуться выполнение после `await` (например, в UI-приложениях — обратно в UI-поток для безопасного доступа к элементам интерфейса). `ConfigureAwait(false)` говорит не возвращаться в исходный контекст, а продолжить на любом доступном потоке из пула — это важно в библиотечном коде (не UI), чтобы избежать ненужных переключений контекста и потенциальных deadlock'ов. В ASP.NET Core (начиная с версии на базе .NET Core) `SynchronizationContext` для запросов отсутствует, поэтому проблема там менее актуальна, чем в classic ASP.NET/WPF/WinForms.

### 6.4. Почему `.Result`/`.Wait()` на асинхронном методе может привести к deadlock?
В окружениях с однопоточным `SynchronizationContext` (classic ASP.NET, WPF, WinForms UI-поток) синхронное блокирование (`.Result`) занимает единственный поток контекста, ожидая завершения задачи. Но `await` внутри вызванного асинхронного метода по умолчанию пытается вернуться в тот же самый (уже заблокированный) `SynchronizationContext` для продолжения — получается взаимная блокировка: вызывающий поток ждёт задачу, а задача не может продолжиться, пока не освободится тот же поток. Решения: `ConfigureAwait(false)` во всей цепочке вызовов, либо `await` вместо `.Result`/`.Wait()` целиком.

```
UI Thread:                     ThreadPool:
1. Call Foo().Result  ─blocks─▶
2. (waiting...)                2. await Bar(); // хочет вернуться в UI thread
                                3. Не может — UI thread занят на шаге 1
        ⇦──────────── DEADLOCK ────────────⇒
```

### 6.5. В чём разница между `Task` и `Task<T>`?
`Task` представляет асинхронную операцию без возвращаемого значения (аналог `void`, но awaitable и с отслеживанием статуса/исключений). `Task<T>` — то же самое, но с результатом типа `T`, доступным через `.Result` (синхронно, блокирующе) или `await` (асинхронно).

### 6.6. Что такое `ValueTask<T>` и когда его стоит использовать вместо `Task<T>`?
`ValueTask<T>` — struct-обёртка, позволяющая избежать heap-аллокации `Task`-объекта в горячих путях, когда результат часто доступен синхронно (например, значение уже в кэше). Требует осторожности: `ValueTask` нельзя await'ить дважды, нельзя одновременно ожидать из нескольких мест (в отличие от `Task`, который можно awaitить многократно/из нескольких точек) — используется, как правило, в высокопроизводительных библиотеках, а не по умолчанию в бизнес-коде.

### 6.7. Что такое `Task.Run` и когда его стоит/не стоит использовать?
`Task.Run` ставит делегат в очередь ThreadPool для выполнения на отдельном потоке — предназначен для CPU-bound работы, которую нужно выполнить, не блокируя текущий поток. Использовать его для оборачивания уже асинхронных I/O-bound операций (например, `Task.Run(() => httpClient.GetAsync(url))`) — антипаттерн: тратится дополнительный поток впустую, так как I/O-bound `await` и без того не блокирует поток. Особенно вреден `Task.Run` внутри ASP.NET Core обработчика запроса (thread-hopping без пользы, "sync-over-async"/"async-over-sync" антипаттерны).

### 6.8. Чем отличаются `lock`, `Monitor`, `Mutex`, `Semaphore`/`SemaphoreSlim`?
`lock (obj)` — синтаксический сахар над `Monitor.Enter`/`Monitor.Exit` (с `try/finally`), взаимное исключение в пределах одного процесса. `Mutex` — то же самое, но может быть именованным и работать между процессами (межпроцессная синхронизация), дороже по производительности. `Semaphore`/`SemaphoreSlim` ограничивает число одновременных "входов" не единицей, а произвольным числом N (например, не более 5 одновременных запросов) — `SemaphoreSlim` дополнительно поддерживает асинхронное ожидание (`WaitAsync`), в отличие от `lock`, который нельзя использовать вокруг `await`.

### 6.9. Почему нельзя использовать `await` внутри блока `lock`?
Компилятор не разрешает `await` внутри `lock`, потому что `lock` привязан к конкретному потоку (Monitor требует, чтобы вход и выход из критической секции происходили в одном потоке), а после `await` продолжение может выполниться на другом потоке из пула — это нарушило бы модель Monitor и могло привести к неопределённому поведению. Альтернатива — `SemaphoreSlim.WaitAsync()`/`ReleaseAsync`-подобные асинхронные примитивы синхронизации.

### 6.10. Что такое race condition и как его избежать?
Состояние гонки — когда результат работы программы зависит от непредсказуемого порядка выполнения потоков, обращающихся к общим данным без должной синхронизации, что приводит к неконсистентным/некорректным результатам. Избегается через синхронизацию доступа (`lock`, `Interlocked`, потокобезопасные коллекции), либо через иммутабельность данных, либо через изоляцию состояния по потокам (`ThreadLocal<T>`, `[ThreadStatic]`).

### 6.11. Что такое deadlock, livelock и starvation?
Deadlock — два и более потока бесконечно ждут друг друга (например, каждый держит ресурс, нужный другому, и ждёт освобождения второго). Livelock — потоки не заблокированы, но постоянно реагируют друг на друга, меняя состояние без прогресса (например, оба уступают дорогу друг другу бесконечно). Starvation — поток постоянно не получает доступа к ресурсу из-за того, что другие потоки с более высоким приоритетом или чаще успевают захватить его первыми.

### 6.12. Как избежать deadlock при множественных `lock`?
Главное правило — всегда захватывать несколько блокировок в одинаковом, заранее согласованном порядке во всех местах кода (например, всегда сначала lockA, потом lockB). Дополнительно можно использовать `Monitor.TryEnter` с таймаутом вместо безусловного `lock`, чтобы не блокироваться бесконечно, либо минимизировать количество одновременно удерживаемых блокировок.

### 6.13. Что такое `Interlocked` и когда он предпочтительнее `lock`?
`Interlocked` предоставляет атомарные операции (`Increment`, `Decrement`, `CompareExchange`, `Add`, `Exchange`) над примитивными типами без использования блокировок ОС — быстрее `lock` для простых атомарных изменений одного значения (счётчики, флаги), так как реализуется через аппаратные атомарные инструкции CPU, а не через операционные примитивы синхронизации.

### 6.14. Что такое TPL (Task Parallel Library) и чем отличается от классических `Thread`?
TPL строится вокруг абстракции `Task`, представляющей единицу асинхронной/параллельной работы, планируемую и исполняемую через `TaskScheduler`/ThreadPool — TPL сам управляет пулом потоков, балансировкой нагрузки (work-stealing), объединением задач в цепочки продолжений (`ContinueWith`), тогда как `Thread` — низкоуровневая, дорогая (по созданию) абстракция ОС-потока без встроенной поддержки результата/композиции/отмены.

### 6.15. Что такое `Parallel.For`/`Parallel.ForEach` и `PLINQ` — для каких задач они подходят?
Оба используют TPL для параллельного выполнения CPU-bound итераций на нескольких ядрах. `Parallel.For/ForEach` — императивный стиль с явным циклом. PLINQ (`.AsParallel()`) — декларативный LINQ-стиль, автоматически распараллеливающий цепочку операторов. Подходят для CPU-bound задач с независимыми итерациями (без сильной взаимозависимости данных); для I/O-bound операций предпочтительнее `async/await` с `Task.WhenAll`, а не параллелизм потоков.

### 6.16. Как работает `CancellationToken` и `CancellationTokenSource`?
`CancellationTokenSource` создаёт токен отмены и управляет его состоянием (`Cancel()`, таймаут через `CancelAfter`). `CancellationToken` передаётся в асинхронные методы, которые периодически проверяют `IsCancellationRequested` или вызывают `ThrowIfCancellationRequested()`, либо передают токен во внутренние awaitable-операции (которые сами прервутся с `OperationCanceledException`). Это кооперативный механизм — код должен сам явно проверять токен, отмена не прерывает выполнение принудительно.

### 6.17. Что такое `Task.WhenAll` и `Task.WhenAny`, чем отличаются от последовательного `await`?
`Task.WhenAll` запускает все задачи параллельно (если они уже были запущены до вызова) и ожидает завершения всех, агрегируя исключения в `AggregateException` при множественных сбоях — значительно быстрее последовательного `await` каждой задачи по очереди для независимых I/O-bound операций. `Task.WhenAny` возвращается, как только завершится любая из задач первой — полезно для таймаутов или "первый ответивший сервер побеждает" сценариев.

### 6.18. Как правильно обрабатывать исключения в async-методах, особенно с `Task.WhenAll`?
`await` перевыбрасывает исключение исходной задачи как есть (не оборачивая в `AggregateException`, в отличие от `.Wait()`/`.Result`). При `await Task.WhenAll(tasks)`, если несколько задач упали, `await` перевыбросит только первое исключение — чтобы увидеть все, нужно проверить `Task.Exception` (это `AggregateException`) у самой задачи `WhenAll` до/вместо await, либо перебрать все задачи после `WhenAll` и собрать их исключения вручную.

### 6.19. Что такое `async void` и почему это антипаттерн (кроме обработчиков событий)?
`async void` методы не возвращают `Task`, поэтому вызывающий код не может их awaitить, не может узнать о завершении или поймать исключение обычным способом — необработанное исключение в `async void` уходит напрямую в `SynchronizationContext`, что обычно приводит к падению процесса. Единственное легитимное применение — обработчики событий UI (`async void Button_Click(...)`), сигнатура которых зафиксирована фреймворком и не может возвращать `Task`.

### 6.20. Что такое thread pool starvation и как его диагностировать?
Возникает, когда все потоки пула заняты (например, синхронно блокирующимися I/O-bound операциями через `.Result`/`.Wait()` вместо `await`), и новым задачам не хватает потоков для выполнения — они встают в очередь и ждут, что приводит к резкому росту латентности. ThreadPool медленно (по одному потоку в ~секунду до .NET-специфичных улучшений) добавляет новые потоки при нехватке, что усугубляет проблему под нагрузкой. Диагностируется через счётчики ThreadPool queue length, `ThreadPool.GetAvailableThreads`, dotnet-counters/dotnet-trace.

### 6.21. Что такое `IAsyncEnumerable<T>` и `await foreach` (C# 8)?
Асинхронный аналог `IEnumerable<T>`/`yield return`, позволяющий лениво генерировать и потреблять последовательность элементов, каждый из которых может быть получен асинхронно (например, постранично из БД/сети), без необходимости ждать загрузки всей коллекции целиком перед началом обработки.
```csharp
async IAsyncEnumerable<int> GetNumbersAsync()
{
    for (int i = 0; i < 5; i++) { await Task.Delay(100); yield return i; }
}
await foreach (var n in GetNumbersAsync()) Console.WriteLine(n);
```

### 6.22. Как работает `ConcurrentDictionary<TKey,TValue>` и другие потокобезопасные коллекции `System.Collections.Concurrent`?
Эти коллекции (`ConcurrentDictionary`, `ConcurrentQueue`, `ConcurrentBag`, `ConcurrentStack`, `BlockingCollection`) реализуют внутреннюю синхронизацию (часто через lock-free алгоритмы с `Interlocked`/сегментированные блокировки), безопасную для одновременного доступа из нескольких потоков без внешнего `lock`. `ConcurrentDictionary` дополнительно предлагает атомарные методы вроде `GetOrAdd`/`AddOrUpdate`, важные для избежания race condition при read-modify-write операциях.

### 6.23. Что такое `volatile` и когда он нужен?
Модификатор поля, отключающий определённые компиляторные и процессорные оптимизации переупорядочивания и кэширования значения в регистрах — гарантирует, что чтение поля всегда идёт из основной памяти, а не из локального кэша потока/регистра. Полезен для простых флагов, читаемых/записываемых из разных потоков без полноценной блокировки, но не заменяет `lock`/`Interlocked` для составных read-modify-write операций.

### 6.24. Что такое `Thread.Sleep` vs `Task.Delay`, и почему в асинхронном коде нужен второй?
`Thread.Sleep` блокирует текущий поток целиком на заданное время — поток простаивает и не может выполнять другую работу. `Task.Delay` возвращает awaitable `Task`, которая завершится через заданное время, не блокируя поток — во время ожидания поток возвращается в пул и может обслуживать другие задачи. В асинхронном коде `Thread.Sleep` — антипаттерн, блокирующий поток впустую.

### 6.25. Как работает планирование задач (TaskScheduler) и в чём разница между `Task.Factory.StartNew` и `Task.Run`?
`Task.Run` — упрощённый, безопасный по умолчанию способ запланировать работу на ThreadPool с разумными настройками (`TaskCreationOptions.DenyChildAttach`, использует `TaskScheduler.Default`). `Task.Factory.StartNew` — более низкоуровневый и гибкий API с полным контролем над `TaskCreationOptions`, `TaskScheduler`, но с менее безопасными настройками по умолчанию (например, не разворачивает автоматически вложенный `Task<Task>`, что часто приводит к багам) — в большинстве случаев рекомендуется `Task.Run`.

## 7. Обработка исключений

### 7.1. Как устроена иерархия исключений в .NET — базовые классы?
Все исключения наследуются от `System.Exception`. Ключевые ветки: `SystemException` (исключения, генерируемые CLR/BCL — `NullReferenceException`, `IndexOutOfRangeException`, `InvalidOperationException`) и рекомендуемая практика — создавать собственные исключения, наследуясь напрямую от `Exception` (а не от `ApplicationException`, использование которой сейчас не рекомендуется Microsoft).

### 7.2. В чём разница между `throw ex` и `throw` внутри `catch`?
`throw;` (без указания переменной) перевыбрасывает исходное исключение, сохраняя оригинальный stack trace — где оно реально произошло. `throw ex;` создаёт впечатление нового исключения "отсюда" — stack trace перезаписывается точкой этого `throw`, теряя информацию о реальном месте возникновения ошибки. Всегда предпочтителен `throw;` при перевыбросе того же исключения.

### 7.3. Когда стоит использовать `try/catch/finally`, а когда — `using`?
`finally` гарантированно выполняется при выходе из `try`-блока (нормальном или через исключение) — используется для произвольной очистки логики. `using` — специализированный синтаксис именно для `IDisposable`-ресурсов, компилируется в `try/finally` с вызовом `Dispose()` — предпочтителен, когда ресурс реализует `IDisposable`, так как короче и явно выражает намерение.

### 7.4. Что такое exception filters (`catch (Exception e) when (condition)`)?
Позволяют условно перехватывать исключение только при выполнении дополнительного предиката, не разворачивая стек, если условие не выполнено (в отличие от перехвата и повторного `throw` внутри — фильтр выполняется до "раскрутки" стека, что важно для отладчиков и логирования исходного состояния стека).
```csharp
try { ... }
catch (HttpRequestException e) when (e.StatusCode == HttpStatusCode.TooManyRequests)
{
    // только для 429
}
```

### 7.5. Почему не стоит перехватывать `catch (Exception)` без веской причины (пустой catch-all)?
Такой перехват маскирует любые ошибки, включая критические (например, `OutOfMemoryException`, ошибки программирования вроде `NullReferenceException`), затрудняя диагностику и потенциально оставляя приложение в некорректном/непредсказуемом состоянии, продолжающем работу как ни в чём не бывало. Правило — перехватывать только конкретные ожидаемые типы исключений, которые вы реально умеете обрабатывать.

### 7.6. В чём стоимость (performance cost) исключений в .NET и почему их не стоит использовать для управления обычным потоком выполнения?
Выброс исключения — относительно дорогая операция (сбор stack trace, разворачивание стека, поиск обработчика) по сравнению с обычным возвратом значения/кодом ошибки — на порядки медленнее обычного `return`. Исключения предназначены для действительно исключительных, непредвиденных ситуаций, а не для штатной логики (например, для проверки существования элемента лучше `TryGetValue`, чем `try/catch` вокруг индексатора).

### 7.7. Что такое `AggregateException` и когда он появляется?
Контейнер для нескольких исключений, возникших одновременно — типично при использовании `Task.WhenAll` через `.Wait()`/`.Result` (не через `await`) или Parallel LINQ, где несколько параллельных операций могут упасть одновременно. `.Flatten()` разворачивает вложенные `AggregateException` в единый плоский список внутренних исключений (`InnerExceptions`).

### 7.8. Как правильно создавать собственные (custom) исключения?
Наследовать от `Exception` (или более специфичного подходящего базового класса), предусмотреть стандартные конструкторы (`()`, `(string message)`, `(string message, Exception inner)`), при необходимости — сериализуемость (для .NET Framework это требовало `[Serializable]` и конструктор с `SerializationInfo`; в современном .NET бинарная сериализация исключений устарела). Добавлять дополнительные свойства с бизнес-контекстом ошибки (например, `OrderId`).
```csharp
public class OrderNotFoundException : Exception
{
    public int OrderId { get; }
    public OrderNotFoundException(int orderId)
        : base($"Order {orderId} not found.") => OrderId = orderId;
}
```

### 7.9. Что такое inner exception и зачем сохранять исходное исключение при обёртывании?
`InnerException` сохраняет цепочку причинности при перевыбросе нового исключения поверх пойманного (`throw new ServiceException("...", ex);`) — без этого теряется исходная причина ошибки (stack trace и тип исходного исключения), что серьёзно усложняет отладку в продакшене.

### 7.10. Каков порядок выполнения при нескольких `catch`-блоках и `finally`?
Блоки `catch` проверяются сверху вниз, срабатывает первый подходящий по типу (более специфичные типы исключений должны идти раньше базовых, иначе базовый `catch` "перехватит" всё и код ниже станет недостижимым — это ошибка компиляции для строго упорядоченных типов). `finally` выполняется всегда после `try`/сработавшего `catch`, независимо от того, было исключение или нет, и даже если внутри `catch`/`try` был `return`.

### 7.11. Что такое `ExceptionDispatchInfo.Capture/Throw` и зачем он нужен?
Позволяет захватить исключение (включая полный stack trace) в одном месте и перевыбросить его позже в другом месте кода с сохранением исходного stack trace — полезно, например, при агрегировании исключений из нескольких задач и последующем перевыбросе одного из них с сохранением диагностической информации, чего простой `throw ex` не позволяет.

### 7.12. Как исключения ведут себя в конструкторах и деструкторах/финализаторах?
Исключение в конструкторе прерывает создание объекта — объект не будет считаться созданным, но если он реализует `IDisposable`, уже инициализированные unmanaged-ресурсы могут "утечь", если не предусмотрена очистка внутри самого конструктора (частично инициализированный объект недоступен для вызова `Dispose()` извне). Исключение в финализаторе в современных версиях CLR приводит к аварийному завершению процесса — финализаторы должны быть максимально надёжными и не бросать исключений.

## 8. Дженерики (Generics)

### 8.1. Зачем нужны дженерики — какие проблемы они решают по сравнению с `object`?
До дженериков переиспользуемые коллекции/алгоритмы работали через `object`, что требовало boxing/unboxing для value types (потеря производительности) и не давало типобезопасности на этапе компиляции (ошибки приведения типов всплывали только в runtime). Дженерики дают типобезопасность на этапе компиляции и устраняют boxing для value types, так как для каждого value-type-параметра JIT генерирует специализированный код.

### 8.2. Как JIT обрабатывает generic-типы для value types vs reference types (специализация кода)?
Для value type-параметров (`List<int>`, `List<MyStruct>`) JIT создаёт отдельную специализированную реализацию машинного кода под каждый конкретный value type при первом использовании (code specialization) — это устраняет boxing, но увеличивает размер сгенерированного кода. Для reference type-параметров (`List<string>`, `List<MyClass>`) JIT переиспользует один и тот же скомпилированный код (так как все ссылки одинакового размера — указатель), подставляя разные типы только на уровне метаданных — экономит память кода за счёт совместного использования.

### 8.3. Что такое generic constraints (`where T : ...`) и какие они бывают?
Ограничения сужают допустимые типы для параметра дженерика и открывают доступ к соответствующим членам внутри generic-кода: `where T : class` (reference type), `where T : struct` (value type), `where T : new()` (публичный parameterless-конструктор), `where T : BaseClass`, `where T : IInterface`, `where T : U` (T должен быть или наследовать U), `where T : notnull` (C# 8+, non-nullable), `where T : unmanaged` (C# 7.3+, unmanaged struct без managed-ссылок внутри).

### 8.4. Чем ковариантные/контравариантные generic-интерфейсы (`out`/`in`) отличаются от обычных дженериков?
Обычный generic-интерфейс инвариантен: `IList<string>` нельзя использовать как `IList<object>`, даже если `string` — производный от `object`, потому что интерфейс допускает и чтение, и запись (запись `object`-совместимого, но не `string`, элемента в `IList<string>` через ссылку типа `IList<object>` нарушила бы типобезопасность). `out T`-параметр (только для возвращаемых значений, ковариантность) и `in T`-параметр (только для входных параметров, контравариантность) гарантируют компилятору однонаправленное использование T, что и делает вариантность безопасной.

### 8.5. Что такое generic-методы и чем они отличаются от generic-типов?
Generic-тип параметризуется на уровне всего класса/структуры/интерфейса (`class Box<T>`). Generic-метод параметризуется независимо на уровне отдельного метода, даже если содержащий класс не является generic (`static T Max<T>(T a, T b) where T : IComparable<T>`) — параметр типа выводится компилятором из аргументов вызова (type inference) в большинстве случаев без явного указания.

### 8.6. Почему нельзя писать `T + T` или создавать `new T[]` без ограничений в generic-методе?
Компилятор не знает конкретный тип T на этапе компиляции — не все типы поддерживают оператор `+` (это статический метод, который надо разрешить на этапе компиляции для конкретного типа) или имеют доступный конструктор. Для операций типа сложения нужны либо ограничения через интерфейсы (`INumber<T>` в .NET 7+ через generic math), либо передача делегата-операции извне.

### 8.7. Что такое "generic math" (`INumber<T>`, .NET 7+) и какую проблему он решает?
Ранее было невозможно написать один generic-метод, работающий арифметически со всеми числовыми типами (`int`, `double`, `decimal`...), так как у них нет общего интерфейса с операторами. .NET 7 ввёл static abstract members в интерфейсах (`INumber<T>`, `IAdditionOperators<T,T,T>` и др.), позволяющие писать единый generic-алгоритм, работающий поверх любого числового типа, реализующего эти интерфейсы, без потери производительности (в отличие от рефлексии/делегатов).

### 8.8. Как работают generic-типы с наследованием — можно ли наследовать закрытый (closed) generic от открытого (open)?
`class IntBox : Box<int> { }` — допустимо (закрытый generic, конкретизирующий параметр). Также допустимо `class DerivedBox<T> : Box<T> { }` (открытый generic наследует открытый generic, параметр "прокидывается" дальше). Нельзя наследовать напрямую от незакрытого generic-параметра без конкретизации вне generic-контекста.

### 8.9. Что такое `default(T)` в generic-коде и почему он ведёт себя по-разному для class/struct T?
Внутри generic-метода компилятор не знает заранее, class T или struct — `default(T)` универсально возвращает `null` для reference type-инстанциаций и "нулевое" значение (все поля по умолчанию) для value type-инстанциаций, что позволяет писать единый код, корректно работающий для обоих случаев.

### 8.10. Как дженерики помогают избежать boxing в коллекциях по сравнению с `ArrayList`?
`ArrayList` хранит элементы как `object` — каждое добавление value type (например, `int`) в него требует boxing (аллокация в heap), а чтение — unboxing. `List<int>` хранит элементы как настоящий типизированный массив `int[]` внутри — никакого boxing не происходит, что даёт существенный выигрыш по памяти и скорости для больших коллекций value types.

### 8.11. Что такое self-referencing generic constraint (CRTP-подобный паттерн, `where T : Base<T>`)?
Паттерн, где базовый generic-класс параметризуется собственным наследником: `abstract class Entity<T> where T : Entity<T>`, позволяющий базовому классу типобезопасно возвращать/оперировать конкретным типом наследника (например, для fluent-API с корректным типом возврата в цепочке вызовов у каждого наследника без явных приведений типов).

### 8.12. Может ли generic-тип иметь несколько параметров типа с разными constraints одновременно?
Да, каждый параметр может иметь собственный независимый набор ограничений: `class Repository<TEntity, TKey> where TEntity : class, IEntity<TKey> where TKey : struct, IEquatable<TKey>`.

### 8.13. Чем `IEnumerable<T>` как generic-интерфейс превосходит негенерик `IEnumerable`?
Generic-версия даёт типобезопасность при переборе (`foreach (string s in items)` без явного каста) и устраняет boxing для value types при переборе, а также позволяет использовать LINQ-операторы напрямую (LINQ определён для `IEnumerable<T>`).

### 8.14. Что такое type inference для generic-методов и когда компилятор не может его вывести?
Компилятор пытается вывести параметры типа generic-метода из типов аргументов вызова, чтобы не указывать их явно (`Max(1, 2)` вместо `Max<int>(1, 2)`). Не может вывести, если тип параметра используется только в возвращаемом значении, а не в параметрах метода — тогда нужно указать тип явно.

### 8.15. Как работает `typeof(T)` внутри generic-метода и почему это иногда медленно?
`typeof(T)` внутри generic-метода на каждом вызове (для каждой инстанциации value type) выполняет относительно недешёвый lookup через `RuntimeTypeHandle`, хотя современный JIT неплохо оптимизирует этот паттерн через кэширование внутри специализированного кода. В горячих путях с большим числом вызовов иногда предпочтительнее кэшировать `Type` в статическом generic-поле (`static readonly Type CachedType = typeof(T);`), которое инициализируется один раз на каждую специализацию.

## 9. Коллекции и структуры данных

### 9.1. Чем `List<T>` отличается от `LinkedList<T>` по сложности операций?
`List<T>` — динамический массив: доступ по индексу O(1), добавление в конец амортизированно O(1) (иногда O(n) при пересоздании внутреннего массива при росте), вставка/удаление в середине O(n) (сдвиг элементов). `LinkedList<T>` — двусвязный список: доступ по индексу O(n) (нет прямого индексатора), но вставка/удаление в известной позиции (по узлу) O(1), без сдвига элементов.

### 9.2. Как устроен `Dictionary<TKey,TValue>` внутри — хэш-таблица с чем?
Массив "бакетов" (buckets), где для каждого ключа вычисляется хэш (`GetHashCode`), по остатку от деления на размер массива определяется бакет; коллизии разрешаются методом цепочек (chaining) через связанный список записей внутри массива `entries` (открытая адресация с цепочками, реализовано через индексы, а не настоящие ссылки-объекты — для эффективности). Средняя сложность операций — O(1) при хорошем распределении хэшей, деградирует до O(n) при массовых коллизиях (плохой `GetHashCode`).

```
buckets: [ 2 | -1 | 0 | 1 ]   (индексы первой записи в цепочке для каждого бакета)
entries: [0: {hash,key,val,next=-1}, 1: {hash,key,val,next=-1}, 2: {hash,key,val,next=0}]
```

### 9.3. Чем `HashSet<T>` отличается от `List<T>` при проверке на содержание элемента?
`HashSet<T>.Contains` — в среднем O(1) благодаря хэш-таблице внутри. `List<T>.Contains` — O(n), линейный перебор. Для частых проверок "содержит ли коллекция элемент" на больших наборах данных `HashSet<T>` значительно эффективнее.

### 9.4. Что такое `SortedList<TKey,TValue>` vs `SortedDictionary<TKey,TValue>`?
Оба хранят элементы отсортированными по ключу. `SortedList` использует внутри два массива (более компактен по памяти, быстрый доступ по индексу O(log n) через бинарный поиск, но вставка/удаление O(n) из-за сдвига). `SortedDictionary` использует красно-чёрное дерево (больше накладных расходов на память из-за узлов дерева, но вставка/удаление O(log n) без сдвигов) — выбор зависит от соотношения частоты вставок/удалений и последовательного построения коллекции.

### 9.5. В чём разница между `Queue<T>`/`Stack<T>` и их concurrent-аналогами?
`Queue<T>` (FIFO) и `Stack<T>` (LIFO) не потокобезопасны. `ConcurrentQueue<T>`/`ConcurrentStack<T>` из `System.Collections.Concurrent` реализуют lock-free алгоритмы для безопасного одновременного доступа из нескольких потоков без внешней блокировки, обычно на основе `Interlocked`-операций и связных структур узлов.

### 9.6. Что такое immutable-коллекции (`System.Collections.Immutable`) и чем они отличаются от `ReadOnlyCollection<T>`?
`ReadOnlyCollection<T>` — просто обёртка "только для чтения" вокруг изменяемой коллекции: сама коллекция неизменяема снаружи, но если исходная (обёрнутая) коллекция изменится, это отразится и в обёртке. Настоящие immutable-коллекции (`ImmutableList<T>`, `ImmutableDictionary<TKey,TValue>`...) при "изменении" создают новую версию структуры данных (persistent data structures, часто через structural sharing для эффективности), исходная версия остаётся неизменной и валидной — полезно для многопоточного доступа без блокировок и функционального стиля программирования.

### 9.7. Как выбрать между `Array`, `List<T>` и `Span<T>` в конкретной ситуации?
`Array` — фиксированный размер, минимальные накладные расходы, если размер известен заранее и не меняется. `List<T>` — динамический размер с удобным API добавления/удаления, небольшие накладные расходы на управление внутренним массивом. `Span<T>` — не отдельная коллекция, а "окно" в существующую память (массив, стек, unmanaged) без копирования и без heap-аллокации — оптимален для временной обработки срезов данных в горячих путях, но ограничен как `ref struct` (нельзя хранить в полях класса, в async-методах).

### 9.8. Почему изменение `Dictionary<TKey,TValue>` во время перебора `foreach` бросает исключение?
Коллекции .NET отслеживают "версию" структуры (счётчик модификаций); enumerator при каждом `MoveNext()` сверяет сохранённую версию с текущей — если коллекция была изменена (добавление/удаление ключа) во время перебора, версия не совпадает и бросается `InvalidOperationException` ("Collection was modified"), чтобы предотвратить непредсказуемое/некорректное поведение итерации по изменяющейся структуре.

### 9.9. Что такое `IReadOnlyList<T>`/`IReadOnlyDictionary<TKey,TValue>` и зачем они нужны при проектировании API?
Интерфейсы, предоставляющие только операции чтения (без Add/Remove), но не гарантирующие полную неизменяемость базового объекта (объект всё ещё может быть изменён через другую ссылку типа `List<T>`, если это тот же самый экземпляр). Используются в сигнатурах публичных API для явного выражения "этот метод не должен и не будет изменять переданную коллекцию" — улучшает читаемость контракта и слегка защищает от случайных модификаций через данную конкретную ссылку.

### 9.10. Чем отличается capacity от count у `List<T>`, и почему это важно для производительности?
`Count` — текущее число элементов. `Capacity` — размер внутреннего массива, выделенного под элементы (может быть больше `Count`). При превышении Capacity `List<T>` пересоздаёт внутренний массив большего размера (обычно удвоение) и копирует все элементы — дорогая операция. Если заранее известен примерный размер коллекции, стоит указать `Capacity` в конструкторе (`new List<T>(expectedSize)`), чтобы избежать многократных перевыделений.

### 9.11. Что такое `ArrayPool<T>` и зачем он нужен?
Пул переиспользуемых массивов (`ArrayPool<T>.Shared.Rent(size)` / `.Return(array)`), позволяющий избежать частых аллокаций и последующей нагрузки на GC (особенно для крупных временных буферов, которые иначе попадали бы в LOH) в высоконагруженных сценариях (парсинг, сетевой ввод-вывод, сериализация).

### 9.12. В чём разница между поверхностным (shallow) и глубоким (deep) копированием коллекций?
Поверхностное копирование (например, `new List<T>(source)`, `Array.Clone()` для массива объектов) копирует сами ссылки на элементы — если элементы reference type, оба списка указывают на одни и те же объекты, изменение через один список отражается на объектах, доступных из другого. Глубокое копирование создаёт независимые копии самих объектов-элементов рекурсивно — реализуется вручную (клонирующий конструктор, `ICloneable` — не рекомендуется Microsoft из-за неоднозначности контракта — или сериализация/десериализация как обходной путь).

### 9.13. Что такое `BitArray` и когда он полезен?
Компактная коллекция для хранения флагов true/false, упаковывающая биты (каждый bool занимает 1 бит вместо байта/более), эффективна по памяти для больших наборов булевых флагов (например, битовые маски, sieve-алгоритмы).

### 9.14. Как реализовать собственную коллекцию, поддерживающую `foreach`?
Реализовать `IEnumerable<T>` (метод `GetEnumerator()`), внутри которого либо вернуть существующий enumerator обёрнутой коллекции, либо использовать `yield return` для собственной ленивой генерации последовательности — компилятор поддерживает `foreach` для любого типа, у которого есть публичный метод `GetEnumerator()`, возвращающий тип с `Current`/`MoveNext()` (не обязательно даже формально реализовывать интерфейс — duck typing для `foreach`).

### 9.15. Чем `Dictionary<TKey,TValue>.TryGetValue` предпочтительнее прямого обращения по индексатору?
Индексатор (`dict[key]`) бросает `KeyNotFoundException`, если ключ отсутствует — дорого (исключения) и требует `try/catch` для штатной проверки существования. `TryGetValue` возвращает `bool` и делает один lookup вместо потенциально двух (проверка `ContainsKey` + отдельный `dict[key]`), избегая как исключений, так и двойного поиска — предпочтительный паттерн.

### 9.16. Что такое frozen-коллекции (`FrozenDictionary`, `FrozenSet`, .NET 8)?
Специализированные неизменяемые коллекции, оптимизированные под сценарий "построить один раз, читать очень часто" — при создании выполняется дополнительная (более затратная, чем у обычного Dictionary) оптимизация внутренней структуры под конкретный набор данных, что даёт заметно более быстрый последующий доступ на чтение по сравнению с обычным `Dictionary`/`ImmutableDictionary`. Подходит для статических справочников, конфигурации, загружаемой один раз при старте приложения.

### 9.17. Как выбрать между `Equals`-based и `ReferenceEquals`-based коллекциями (например, `HashSet<T>` с кастомным `IEqualityComparer<T>`)?
По умолчанию reference type сравнивается по ссылке, если не переопределены `Equals`/`GetHashCode`. Если для reference-типа в конкретном сценарии (например, в конкретном `HashSet<T>`) нужна семантика сравнения "по значению" без изменения самого класса — передаётся кастомный `IEqualityComparer<T>` в конструктор коллекции, не затрагивая поведение `==`/`Equals` типа во всех остальных местах кода.

### 9.18. Что такое `PriorityQueue<TElement,TPriority>` (.NET 6+) и для каких задач он полезен?
Встроенная реализация кучи (min-heap по умолчанию), где элементы извлекаются в порядке возрастания приоритета — полезна для алгоритмов вроде Дейкстры, планировщиков задач, обработки событий по времени, где нужно эффективно (O(log n) вставка/извлечение минимума) получать "следующий по важности" элемент без сортировки всей коллекции целиком заново при каждом изменении.

## 10. SOLID и принципы проектирования

### 10.1. Расшифруйте и кратко опишите каждый принцип SOLID.
S — Single Responsibility (у класса должна быть одна причина для изменения). O — Open/Closed (открыт для расширения, закрыт для модификации). L — Liskov Substitution (объект производного типа должен быть взаимозаменяем с объектом базового типа без нарушения корректности программы). I — Interface Segregation (много узких специализированных интерфейсов лучше одного "толстого"). D — Dependency Inversion (зависимость от абстракций, а не от конкретных реализаций; модули верхнего уровня не должны зависеть от модулей нижнего уровня напрямую).

### 10.2. Приведите пример нарушения Single Responsibility Principle и его исправления.
Нарушение: класс `Order`, который одновременно хранит данные заказа, считает налоги, формирует PDF-счёт и отправляет email — у него множество причин для изменения (изменение налогового законодательства, формата PDF, почтового провайдера). Исправление: выделить `TaxCalculator`, `InvoicePdfGenerator`, `EmailNotifier` как отдельные классы с единственной ответственностью, а `Order` оставить только с данными и бизнес-инвариантами заказа.

### 10.3. Как Open/Closed Principle реализуется на практике в C# (через что)?
Обычно через абстракции (интерфейсы/абстрактные классы) и полиморфизм: вместо `if/switch` по типу с изменением существующего кода при добавлении нового варианта — вводится интерфейс `IDiscountStrategy`, и новый вариант скидки добавляется новым классом-реализацией, без изменения кода, который этой абстракцией пользуется (например, кода корзины заказа).

### 10.4. Что нарушает Liskov Substitution Principle — классический пример "Прямоугольник/Квадрат"?
Если `Square` наследует `Rectangle` и переопределяет `SetWidth`/`SetHeight` так, что изменение одной стороны всегда меняет и другую (чтобы остаться квадратом), это нарушает ожидания кода, работающего с `Rectangle` (который предполагает независимое изменение ширины и высоты) — подстановка `Square` вместо `Rectangle` меняет поведение программы неожиданным образом, что и есть нарушение LSP.

### 10.5. Как обнаружить нарушение LSP в код-ревью?
Красные флаги: переопределённый метод бросает исключение там, где базовый метод его не бросал (`NotSupportedException` в наследнике); переопределённый метод сужает набор допустимых входных значений (сильнее pre-condition) или ослабляет гарантии результата (слабее post-condition) по сравнению с базовым; проверки `is`/`GetType()` на конкретный производный тип в коде, работающем с базовым типом (признак, что базовая абстракция не полностью взаимозаменяема).

### 10.6. Приведите пример нарушения Interface Segregation Principle.
"Толстый" интерфейс `IWorker` с методами `Work()`, `Eat()`, `Sleep()`, который вынужден реализовывать класс `RobotWorker`, не умеющий "есть" и "спать" — приходится реализовывать пустые/бросающие исключение методы. Исправление: разделить на `IWorkable`, `IFeedable`, `ISleepable`, и `RobotWorker` реализует только `IWorkable`.

### 10.7. Как Dependency Inversion Principle связан с Dependency Injection — это одно и то же?
Нет, это разные, хотя и связанные концепции. DIP — принцип проектирования: высокоуровневые модули должны зависеть от абстракций, а не от низкоуровневых деталей реализации. Dependency Injection — один из конкретных технических механизмов реализации DIP на практике (передача зависимостей через конструктор/свойство/метод вместо создания их внутри класса через `new`), но DIP можно реализовать и без DI-контейнера (например, вручную через service locator или factory).

### 10.8. Что такое принцип DRY (Don't Repeat Yourself) и в чём риск его чрезмерного применения?
DRY — избегание дублирования знаний/логики в кодовой базе (одна и та же бизнес-правило должно существовать в одном месте). Риск чрезмерного применения — преждевременная абстракция двух случайно похожих, но концептуально независимых кусков кода в общий метод/класс, что создаёт ложную связанность (изменение по одной причине начинает требовать аккуратности из-за побочного влияния на другой, изначально не связанный сценарий) — иногда осознанное дублирование лучше неверной абстракции ("Rule of Three" — абстрагировать после третьего повторения, а не сразу после второго).

### 10.9. Что такое YAGNI (You Aren't Gonna Need It) и KISS?
YAGNI — не добавлять функциональность/абстракции "про запас", пока в них нет реальной текущей необходимости — избегает overengineering. KISS (Keep It Simple, Stupid) — предпочитать простое решение сложному, если оба решают задачу одинаково хорошо; сложность должна быть оправдана реальными требованиями, а не "на будущее".

### 10.10. Что такое закон Деметры (Law of Demeter, "не разговаривай с незнакомцами")?
Принцип: объект должен вызывать методы только у "непосредственно известных" ему объектов (себя, своих полей, параметров метода, созданных в методе объектов), избегая длинных цепочек вызовов через чужие внутренние объекты (`order.Customer.Address.City.Name` — нарушение). Такие цепочки создают жёсткую связанность со внутренней структурой чужих объектов; предпочтительнее делегирующий метод (`order.GetCustomerCityName()`).

### 10.11. Что такое Composition Root в контексте DI и SOLID?
Единая точка (обычно рядом с точкой входа приложения — `Program.cs`/конфигурация DI-контейнера), где происходит связывание всех зависимостей (регистрация интерфейсов с реализациями) — весь остальной код приложения не знает о конкретных реализациях, только об абстракциях, что и обеспечивает соблюдение DIP на уровне всего приложения, а не отдельного класса.

### 10.12. Как принципы SOLID помогают в написании unit-тестов?
SRP делает классы маленькими и сфокусированными — их проще тестировать изолированно с минимальным числом сценариев. DIP/абстракции позволяют подменять реальные зависимости (БД, сеть) тестовыми дублёрами (mock/stub) через внедрение зависимостей, не завися от реальной инфраструктуры в unit-тестах. ISP снижает число методов, которые нужно "заглушить" в тестовом дублёре реализации интерфейса.

## 11. Паттерны проектирования (GoF)

### 11.1. В чём разница между порождающими (creational), структурными (structural) и поведенческими (behavioral) паттернами?
Порождающие паттерны (Singleton, Factory Method, Abstract Factory, Builder, Prototype) решают задачу гибкого и контролируемого создания объектов. Структурные (Adapter, Decorator, Facade, Proxy, Composite, Bridge, Flyweight) — задачу компоновки объектов/классов в более крупные структуры без потери гибкости. Поведенческие (Strategy, Observer, Command, State, Template Method, Chain of Responsibility, Mediator, Iterator, Visitor, Memento) — задачу распределения ответственности и алгоритмов поведения между объектами.

```
Creational      Structural       Behavioral
Singleton       Adapter          Strategy
Factory Method   Decorator        Observer
Abstract Factory Facade           Command
Builder          Proxy            State
Prototype        Composite        Template Method
                 Bridge           Chain of Responsibility
                 Flyweight        Mediator / Iterator / Visitor / Memento
```

### 11.2. Как правильно реализовать потокобезопасный Singleton в C#?
Самый простой и надёжный способ в современном C# — через `Lazy<T>`, который сам гарантирует потокобезопасную однократную инициализацию по умолчанию.
```csharp
public sealed class Logger
{
    private static readonly Lazy<Logger> _instance = new(() => new Logger());
    public static Logger Instance => _instance.Value;
    private Logger() { }
}
```
Альтернатива — статический конструктор (CLR гарантирует, что он выполнится ровно один раз и потокобезопасно перед первым использованием типа), если инициализация должна быть eager (не ленивой).

### 11.3. В чём разница между Factory Method и Abstract Factory?
Factory Method — один метод (часто виртуальный/абстрактный в базовом классе), инкапсулирующий создание одного вида продукта, переопределяемый наследниками для выбора конкретного класса. Abstract Factory — интерфейс с несколькими методами для создания семейства связанных объектов (например, `ICreateButton`, `ICreateCheckbox` для UI-темы), обеспечивающий, что все созданные объекты одной фабрикой согласованы между собой (принадлежат одному "семейству"/стилю).

### 11.4. Чем Builder отличается от простого конструктора с множеством параметров?
Builder решает проблему "telescoping constructor" (конструктор с десятком опциональных параметров, из-за чего вызов нечитаем и подвержен ошибкам порядка аргументов) — предоставляет пошаговый fluent-API для настройки объекта перед его финальным созданием (`.Build()`), особенно полезен, когда объект должен собираться поэтапно или из разных источников, либо когда часть комбинаций параметров невалидна и должна проверяться по ходу настройки.
```csharp
var pizza = new PizzaBuilder().WithSize(Size.Large).AddTopping("Cheese").Build();
```

### 11.5. Как реализуется Decorator в C# и чем он отличается от наследования?
Decorator оборачивает объект в другой объект той же абстракции, добавляя поведение до/после делегирования вызова обёрнутому объекту — в отличие от наследования, декораторы можно комбинировать динамически в runtime в любом порядке и количестве, не создавая экспоненциальное число подклассов под каждую комбинацию возможностей. Классический пример в BCL — `Stream` (`BufferedStream`, `GZipStream`, `CryptoStream` оборачивают друг друга).

### 11.6. Что такое паттерн Strategy и как его реализовать через делегаты вместо интерфейсов?
Strategy инкапсулирует семейство взаимозаменяемых алгоритмов за общим интерфейсом, позволяя выбирать конкретный алгоритм в runtime. В C# для простых (stateless, однометодных) стратегий часто достаточно `Func<T,TResult>`/`Action<T>` вместо полноценной иерархии классов с интерфейсом (см. также 4.10) — полноценный интерфейс оправдан, когда стратегия требует состояния или нескольких связанных методов.

### 11.7. Как работает паттерн Observer, и как `event` в C# реализует его "из коробки"?
Observer определяет зависимость "один-ко-многим": при изменении состояния субъекта все подписанные наблюдатели уведомляются автоматически. Механизм `event`/делегаты в C# — встроенная поддержка этого паттерна на уровне языка: издатель объявляет `event`, подписчики регистрируют обработчики через `+=`, при наступлении события вызывается `Invoke()`/делегат, что уведомляет всех подписчиков без явной реализации интерфейсов `ISubject`/`IObserver` (хотя `IObservable<T>`/`IObserver<T>` из Rx тоже доступны для более сложных реактивных сценариев).

### 11.8. Чем Adapter отличается от Facade?
Adapter преобразует интерфейс одного (обычно существующего, несовместимого) класса в интерфейс, ожидаемый клиентским кодом — решает проблему несовместимости API (например, обёртка над сторонней библиотекой под нужный вашему коду интерфейс). Facade предоставляет упрощённый унифицированный интерфейс поверх сложной подсистемы с множеством классов, не меняя и не адаптируя их API, а просто скрывая сложность за одним простым фасадным классом.

### 11.9. Что такое паттерн Command и где он применяется в реальных проектах?
Command инкапсулирует запрос/действие (включая все нужные для его выполнения данные) как отдельный объект — позволяет параметризовать клиентов разными запросами, ставить их в очередь, логировать и поддерживать отмену операций (undo/redo). Применяется в реализации меню-действий UI, очередей задач, MediatR-подобных CQRS-библиотек (`IRequest`/`IRequestHandler` — вариация Command).

### 11.10. Что такое паттерн State и чем он отличается от простого `switch` по enum-состоянию?
State инкапсулирует поведение, зависящее от текущего состояния объекта, в отдельные классы-состояния, реализующие общий интерфейс — переключение состояния делегируется самим объектам-состояниям (каждое состояние "знает", в какое следующее оно может перейти), избегая разрастающегося `switch/if` по enum во множестве мест кода при добавлении новых состояний/переходов (соответствует Open/Closed Principle — новое состояние добавляется новым классом).

### 11.11. Что такое Chain of Responsibility и как его использовать для конвейера обработки запросов?
Каждый обработчик в цепочке решает, может ли он обработать запрос сам, и если нет — передаёт его следующему обработчику в цепочке; отправитель не знает заранее, кто именно обработает запрос. ASP.NET Core middleware-конвейер — практический пример этого паттерна: каждый middleware может обработать запрос сам и/или передать его дальше по цепочке `next()`.

### 11.12. Чем Proxy отличается от Decorator, если оба "оборачивают" объект?
Оба структурно похожи (оборачивание объекта той же абстракцией), но по назначению разные: Proxy контролирует доступ к объекту (ленивая инициализация — Virtual Proxy, проверка прав — Protection Proxy, удалённый вызов — Remote Proxy), обычно не добавляя новой функциональности сверх контроля доступа. Decorator именно добавляет/расширяет поведение обёрнутого объекта дополнительной ответственностью, не контролируя доступ к нему.

### 11.13. Что такое паттерн Mediator и как он снижает связанность между объектами?
Mediator инкапсулирует взаимодействие множества объектов в отдельном объекте-посреднике — объекты общаются не напрямую друг с другом (что создало бы связанность "каждый с каждым", many-to-many), а через медиатор, что снижает связанность до "каждый с медиатором" — легче добавлять/менять участников взаимодействия. Библиотека MediatR в .NET реализует этот паттерн для развязки отправителей запросов от их обработчиков.

### 11.14. Что такое Repository и Unit of Work и как они соотносятся с EF Core `DbContext`?
Repository абстрагирует доступ к данным за интерфейсом, скрывая детали конкретного хранилища (позволяет подменить реализацию/замокать для тестов). Unit of Work координирует несколько операций как одну атомарную транзакцию и отслеживает изменения для последующего сохранения одним вызовом. `DbContext` в EF Core уже сам по себе во многом реализует оба паттерна (`DbSet<T>` — репозиторий, `SaveChanges()` — unit of work) — обёртывание его дополнительным собственным Repository/UoW слоем спорно и иногда избыточно, если не нужна полная независимость от EF Core как технологии.

### 11.15. Когда паттерны проектирования становятся антипаттерном (overengineering)?
Когда паттерн применяется "для галочки" без реальной вариативности/потребности в гибкости, которую он призван обеспечить — добавляет косвенность (indirection), абстракции и файлы без соответствующей практической пользы, усложняя чтение и понимание кода больше, чем экономит в будущем. Правило: вводить паттерн, когда реальная (не гипотетическая) потребность в его гибкости уже назрела или крайне вероятна, а не заранее "про запас".

## 12. CLR, сборки, JIT, рефлексия

### 12.1. Что такое CLR, CTS и CLS?
CLR (Common Language Runtime) — исполняющая среда .NET: управляет памятью (GC), исполнением кода (JIT), безопасностью, обработкой исключений. CTS (Common Type System) — унифицированная система типов, общая для всех .NET-языков (C#, F#, VB.NET), обеспечивающая их взаимную совместимость. CLS (Common Language Specification) — подмножество правил CTS, следуя которым публичный API библиотеки гарантированно останется совместимым с любым .NET-языком (например, запрет на публичные члены, отличающиеся только регистром, так как не все языки регистрозависимы).

### 12.2. Как происходит компиляция и выполнение C#-кода — от исходников до выполнения?
1) Компилятор Roslyn компилирует C#-код в промежуточный язык (IL/MSIL) и метаданные, упакованные в сборку (.dll/.exe). 2) При запуске CLR загружает сборку, JIT-компилятор транслирует IL-код метода в нативный машинный код непосредственно перед первым вызовом этого метода (just-in-time), с последующим кэшированием результата на время работы процесса.

```
.cs файлы → Roslyn (C# compiler) → IL + метаданные (сборка .dll/.exe)
                                          │
                                       CLR загружает сборку
                                          │
                                  JIT компилирует IL → нативный код (по требованию)
                                          │
                                     Выполнение на CPU
```

### 12.3. Чем JIT отличается от AOT (Ahead-Of-Time) компиляции, и что такое ReadyToRun/Native AOT?
JIT компилирует код в машинные инструкции динамически во время выполнения — быстрый старт разработки, оптимизации под конкретное железо в runtime, но время "разогрева" (стартовая задержка на компиляцию горячих методов). AOT компилирует весь код в нативный машинный код заранее, на этапе публикации — быстрый холодный старт, отсутствие JIT-задержек, но менее гибкая рантайм-оптимизация. ReadyToRun — гибрид (предкомпилированный код + возможность JIT-перекомпиляции при необходимости). Native AOT (.NET 7+) — полностью нативная компиляция без CLR JIT вообще, значительно меньшее время старта и footprint, но с ограничениями (нет полной поддержки рефлексии/динамической загрузки сборок).

### 12.4. Что такое сборка (Assembly), манифест сборки, и strong name?
Сборка — единица развёртывания и версионирования в .NET (.dll/.exe), содержащая IL-код, метаданные о типах и манифест (информация о версии, зависимых сборках, экспортируемых типах, культуре для локализации). Strong name — криптографическая подпись сборки публичным/приватным ключом, обеспечивающая уникальную идентификацию и защиту от подмены — исторически важна для GAC (Global Assembly Cache) в .NET Framework, менее актуальна в современном .NET с NuGet/self-contained deployment.

### 12.5. Что такое рефлексия (Reflection) и для чего она используется?
API (`System.Reflection`), позволяющий исследовать метаданные типов (методы, свойства, атрибуты) и вызывать их динамически в runtime без знания конкретного типа на этапе компиляции. Используется в сериализаторах, DI-контейнерах, ORM, unit-test фреймворках, ASP.NET Core (для обнаружения контроллеров/маршрутов), плагинных архитектурах.
```csharp
Type t = typeof(MyClass);
var instance = Activator.CreateInstance(t);
var method = t.GetMethod("DoSomething");
method.Invoke(instance, null);
```

### 12.6. Почему рефлексия медленнее прямых вызовов, и как это компенсировать?
`MethodInfo.Invoke` выполняет проверки безопасности, boxing аргументов value types, разрешение метода по метаданным на каждый вызов — на порядки медленнее прямого вызова. Компенсируется: кэшированием `MethodInfo`/`PropertyInfo` (не искать заново на каждый вызов), использованием скомпилированных `Expression Trees` или `Delegate.CreateDelegate` для создания быстрого типизированного делегата один раз и его многократного переиспользования, либо source generators (генерация кода на этапе компиляции вместо рефлексии в runtime).

### 12.7. Что такое атрибуты (Attributes) и как создать собственный?
Декларативные метаданные, прикрепляемые к элементам кода (`[Obsolete]`, `[Serializable]`, `[Route("api/[controller]")]`), читаемые через рефлексию в runtime или используемые компилятором/анализаторами на этапе компиляции. Собственный атрибут — класс, наследующий `System.Attribute`, обычно с `[AttributeUsage]`, задающим допустимые цели применения (класс, метод, свойство и т.д.).
```csharp
[AttributeUsage(AttributeTargets.Method)]
public class RetryAttribute : Attribute { public int Times { get; set; } = 3; }
```

### 12.8. Что такое source generators (C# 9+) и чем они лучше рефлексии для генерации кода?
Компонент компилятора Roslyn, выполняющийся во время компиляции и генерирующий дополнительный C#-код на основе анализа существующего кода (атрибутов, синтаксического дерева) — сгенерированный код становится частью сборки и компилируется обычным путём. В отличие от рефлексии (runtime overhead, риск ошибок только в runtime), source generators не имеют накладных расходов в runtime, ошибки генерации выявляются на этапе компиляции, а сгенерированный код доступен для отладки. Используются, например, в `System.Text.Json` (`[JsonSerializable]`) для AOT-совместимой сериализации без рефлексии.

### 12.9. Что такое AppDomain, и почему в .NET (Core) от него практически отказались?
В .NET Framework `AppDomain` — изолированный контейнер для загрузки сборок и выполнения кода внутри одного процесса, с возможностью выгрузки без остановки процесса. В .NET (Core) единственный полноценный `AppDomain` на процесс — вместо множественных AppDomain для изоляции используется `AssemblyLoadContext`, дающий похожую функциональность (загрузка/выгрузка сборок, изоляция версий зависимостей плагинов) с меньшими накладными расходами и большей кросс-платформенностью.

### 12.10. Что такое `dynamic` в C#, и как он отличается от `object` и рефлексии?
`dynamic` отключает статическую проверку типов на этапе компиляции — разрешение членов (методов/свойств) откладывается до runtime через Dynamic Language Runtime (DLR), используя механизм, похожий на рефлексию, но с кэшированием call site (`CallSite<T>`) для ускорения повторных вызовов того же паттерна. В отличие от `object`, где для вызова члена всегда нужен явный каст, `dynamic` позволяет писать код так, будто тип известен, но ошибка обнаружится только в runtime (не на этапе компиляции), если член не существует.

### 12.11. Как работает загрузка сборок (Assembly Loading) и почему может возникать `FileNotFoundException`/version conflict?
CLR разрешает зависимости сборки по имени, версии, культуре, публичному ключу на основе `runtimeconfig.json`/`deps.json` (.NET Core) — если требуемая версия зависимости отсутствует или конфликтует с версией, использованной другим пакетом (diamond dependency problem), может возникнуть ошибка загрузки или (в лучшем случае, если binding redirect/unification настроены) загрузится совместимая, но не точно та версия. Решается через явные версии в csproj, `<AssemblyBindingRedirect>` (Framework) или unification правил SDK-style проектов (.NET Core автоматически выбирает старшую совместимую версию из графа зависимостей).

### 12.12. Что такое managed vs unmanaged код и как они взаимодействуют через P/Invoke?
Managed-код выполняется под управлением CLR (GC, проверка типов, безопасность). Unmanaged-код — обычный нативный код (C/C++, ОС API), не управляемый CLR. P/Invoke (`[DllImport]`) позволяет managed-коду вызывать функции из unmanaged-библиотек (DLL/so), с маршалингом (marshaling) данных между managed- и unmanaged-представлениями типов (например, строки, структуры) на границе вызова.

### 12.13. Что такое Intermediate Language (IL) и зачем разработчику уметь его читать (например, через ildasm/sharplab)?
IL — платформонезависимый байт-код, в который компилируется весь .NET-код перед JIT-компиляцией в нативный. Умение читать IL (через `ildasm`, `dotnet-il`, sharplab.io) полезно для понимания того, что реально генерирует компилятор из синтаксического сахара (например, как устроен `async` state machine, разница между `struct` и `class` на низком уровне, эффект `sealed` на девиртуализацию) — помогает объяснять производительность и находить неожиданное поведение компилятора.

## 13. Строки и работа с текстом

### 13.1. Почему `string` в .NET неизменяем (immutable), и какие у этого плюсы/минусы?
Каждая "модификация" строки (конкатенация, `Replace`, `Substring`) на самом деле создаёт новый объект строки в heap, оставляя исходную строку без изменений. Плюсы: потокобезопасность по умолчанию (можно свободно шарить строки между потоками без блокировок), безопасность как ключа `Dictionary`/элемента `HashSet` (хэш не "уплывёт"), возможность безопасного string interning. Минус: частые конкатенации в цикле создают множество промежуточных объектов-мусора, нагружая GC.

### 13.2. Чем `StringBuilder` лучше конкатенации строк в цикле?
`StringBuilder` использует внутренний изменяемый буфер (обычно `char[]`), к которому дописываются новые данные без создания нового объекта на каждой операции (амортизированно, с редким перевыделением буфера при росте, аналогично `List<T>`) — конкатенация `str += x` в цикле из N итераций создаёт O(n) промежуточных строк-мусора (сложность O(n²) по суммарно скопированным символам), тогда как `StringBuilder` — O(n) амортизированно.

### 13.3. Что такое string interning (`String.Intern`) и пул строк?
CLR поддерживает внутренний пул уникальных строковых литералов (intern pool) — все одинаковые строковые литералы в коде автоматически ссылаются на один и тот же объект в памяти (компилятор/CLR делает это автоматически для литералов). `String.Intern(str)` позволяет вручную добавить произвольную (не литеральную) строку runtime в этот пул и получить общую ссылку, если такая строка уже там есть — экономит память при множестве повторяющихся строк рантайма, но добавленные вручную интернированные строки живут до конца процесса (не собираются GC), что может стать утечкой при неосторожном использовании.

### 13.4. Как правильно сравнивать строки с учётом культуры (culture) и регистра?
`string.Equals(a, b, StringComparison.Ordinal)` — побайтовое (по code unit) сравнение, самое быстрое и предсказуемое, рекомендуется по умолчанию для технических сравнений (ключи, идентификаторы, пути). `StringComparison.OrdinalIgnoreCase` — то же самое, без учёта регистра ASCII/Unicode по code point. Culture-aware сравнения (`StringComparison.CurrentCulture`/`InvariantCulture`) учитывают лингвистические правила сортировки конкретной локали — нужны для отображения пользователю (например, сортировка списка в UI), но непредсказуемы/неподходящи для бизнес-логики сравнения идентификаторов.

### 13.5. Чем интерполированные строки (`$"..."`) отличаются от `string.Format` по производительности?
Компилятор в простых случаях транслирует `$"Hello {name}"` в `string.Format`/конкатенацию `string.Concat`, но начиная с C# 10 с поддержкой `DefaultInterpolatedStringHandler` компилятор может генерировать более эффективный код, использующий `StringBuilder`-подобный handler напрямую без промежуточных boxing/массивов аргументов `object[]`, что даёт заметный прирост производительности, особенно в горячих путях логирования (аналогично, поддерживается ленивое форматирование — интерполяция не вычисляется вовсе, если, например, уровень логирования отключён и вызывается специальный overload).

### 13.6. Что такое `ReadOnlySpan<char>` и как он помогает избежать лишних аллокаций при парсинге строк?
Позволяет работать со "срезом" существующей строки (или другого источника памяти char) без создания новой строки-подстроки — `str.AsSpan(start, length)` вместо `str.Substring(start, length)`, которая создаёт новый объект строки в heap. Особенно полезно в парсерах, обрабатывающих большие строки/файлы по частям без множества промежуточных аллокаций подстрок.

### 13.7. Как работают `string.Split`, `string.Join` и в чём их частые ошибки использования (например, лишние аллокации)?
`Split` создаёт новый массив строк и по одной строке-подстроке на каждый сегмент — на больших/часто вызываемых строках может быть источником заметных аллокаций; альтернатива для парсинга без аллокаций — `MemoryExtensions.Split`/ручной проход по `ReadOnlySpan<char>` с `IndexOf`. `Join` объединяет элементы через разделитель эффективно (внутри использует построение через известную суммарную длину), но частая ошибка — вызывать `Join`/`Split` многократно в цикле там, где можно один раз собрать результат через `StringBuilder`.

### 13.8. Чем `Encoding.UTF8`, `Encoding.Unicode` (UTF-16) отличаются, и почему `string` в .NET хранится как UTF-16?
Внутреннее представление `string` в .NET — последовательность `char` (UTF-16 code units, 2 байта на code unit; символы вне Basic Multilingual Plane представлены суррогатной парой из двух `char`). `Encoding.UTF8`/`Encoding.Unicode`(UTF-16 LE) — классы для преобразования между этим внутренним представлением и байтовыми представлениями при вводе-выводе (файлы, сеть) — важно явно указывать кодировку при чтении/записи текста, чтобы избежать искажения не-ASCII символов ("кракозябры").

### 13.9. Что такое verbatim string (`@"..."`) и raw string literal (`"""..."""`, C# 11)?
Verbatim string (`@"C:\path"`) отключает интерпретацию escape-последовательностей (`\n`, `\t`), кроме удвоенных кавычек (`""`) для экранирования самой кавычки — удобно для путей файлов, регулярных выражений. Raw string literals (C# 11, `"""текст с "кавычками" и \n без экранирования"""`) идут ещё дальше — вообще не требуют экранирования ничего, включая кавычки, что особенно удобно для встраивания JSON/XML/regex-шаблонов прямо в код без визуального шума экранирования.

### 13.10. Как эффективно проверить, что строка состоит только из цифр/букв без регулярных выражений?
Для простых проверок эффективнее ручной проход по `ReadOnlySpan<char>` с `char.IsDigit`/`char.IsLetter` без выделения памяти и без накладных расходов на компиляцию/выполнение regex-движка, который оправдан для сложных шаблонов, но избыточен для тривиальных посимвольных проверок.

Ресурсы: [Strings — MS Learn](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/strings/) · [Best practices for string comparison](https://learn.microsoft.com/en-us/dotnet/standard/base-types/best-practices-strings)

## 14. Nullable-типы и null-safety

### 14.1. Чем `Nullable<T>` (`int?`) отличается от nullable reference types (`string?`)?
`Nullable<T>` (`int?`) — реальная runtime-обёртка (struct с полями `HasValue`/`Value`) над value type, позволяющая value type принимать значение null — это runtime-функциональность, существующая с .NET 2.0. Nullable reference types (`string?`, C# 8+) — чисто compile-time функция статического анализа компилятора (аннотации и предупреждения), не меняющая runtime-поведение вообще — `string?` и `string` в runtime абсолютно идентичны (оба могут содержать null), разница только в предупреждениях компилятора при потенциальном разыменовании null.

### 14.2. Как устроен `Nullable<T>` внутри?
Struct с двумя полями: `bool hasValue` и `T value`. `HasValue` показывает, есть ли значение, `Value` бросает `InvalidOperationException`, если обратиться к нему при `HasValue == false`. Оператор `??`/сравнение с `null` и boxing `Nullable<T>` в `object` обрабатываются CLR специальным образом (boxing `null`-состояния `Nullable<T>` даёт настоящий `null`, а не boxed-структуру с `HasValue = false`).

### 14.3. Как включить Nullable Reference Types в проекте и что это меняет?
`<Nullable>enable</Nullable>` в csproj (или `#nullable enable` в файле). После включения компилятор считает все reference-типы non-nullable по умолчанию (`string`) и требует явной аннотации `?` (`string?`) для типов, допускающих null — далее статически анализирует поток данных (flow analysis) и выдаёт предупреждения при возможном разыменовании потенциально null значения без предварительной проверки.

### 14.4. Что такое null-forgiving оператор (`!`) и когда он оправдан?
`value!` подавляет предупреждение компилятора о возможном null для конкретного выражения, утверждая разработчиком, что он точно знает — здесь значение не будет null, хотя статический анализатор не может это доказать (например, после кастомной проверки, не распознаваемой flow-анализом, или сразу после `[MemberNotNull]`-неаннотированного метода). Не влияет на runtime — это чисто подавление предупреждения компилятора, при реальном null всё равно будет `NullReferenceException`.

### 14.5. Чем `??` отличается от `?.` и `??=`?
`??` (null-coalescing) — возвращает левый операнд, если он не null, иначе правый (`a ?? b`). `?.` (null-conditional) — вызывает член/индексатор только если объект слева не null, иначе всё выражение целиком возвращает null без исключения (`obj?.Method()`). `??=` (C# 8, null-coalescing assignment) — присваивает правую часть переменной, только если она сейчас null (`x ??= new List<int>();`).

### 14.6. Что такое атрибуты null-анализа (`[NotNull]`, `[MaybeNull]`, `[NotNullWhen]`, `[MemberNotNull]`) и зачем они нужны?
Позволяют явно описать компилятору null-поведение методов, не выражаемое напрямую в сигнатуре типа — например, `bool TryGetValue([NotNullWhen(true)] out string? value)` говорит анализатору, что если метод вернул `true`, `value` гарантированно не null (даже несмотря на объявленный тип `string?`). Используются в BCL (`string.IsNullOrEmpty` помечен `[NotNullWhen(false)]` для проверяемого параметра) и полезны в собственных TryXxx/валидационных методах для точной работы flow-анализа у потребителей.

### 14.7. Почему nullable reference types — это "просто предупреждения", а не гарантия отсутствия `NullReferenceException`?
Аннотации проверяются только статическим анализом компилятора в собственном коде — они не предотвращают null runtime-физически (в отличие, например, от типов с ненулевыми гарантиями в некоторых других языках на уровне runtime). Внешние библиотеки без nullable-аннотаций, десериализация из JSON, рефлексия, приведение через `!` или `(string)(object)null` — всё это может дать реальный null в переменной, объявленной как non-nullable, минуя предупреждения компилятора.

### 14.8. Как правильно спроектировать API, чтобы минимизировать риск `NullReferenceException` у потребителей?
Использовать non-nullable reference types по умолчанию (включённый nullable context), явно возвращать `T?` только там, где отсутствие значения — валидный сценарий, предпочитать `TryGetX(out T value)` паттерн вместо возврата null для "не найдено", использовать null-object паттерн (возврат пустой коллекции вместо null для методов, возвращающих коллекции), валидировать параметры конструктора/публичных методов через `ArgumentNullException.ThrowIfNull(param)` (.NET 6+) в самом начале метода.

### 14.9. Что такое `required` модификатор (C# 11) и как он связан с null-safety?
`required` на свойстве обязывает потребителя инициализировать это свойство через object initializer при создании объекта (`new Person { Name = "..." }` — компилятор ошибётся, если `required`-свойство не задано) — компилятор гарантирует на этапе компиляции, что non-nullable required-свойство не останется со значением по умолчанию/null, что дополняет nullable reference types для случаев, когда конструктор без параметров/object initializer используется вместо обязательного конструктора с параметрами.

### 14.10. Как ведут себя nullable value types и nullable reference types при сериализации (например, System.Text.Json)?
Для nullable value types (`int?`) сериализатор естественно поддерживает `null` в JSON, десериализуя в `HasValue = false`. Для non-nullable reference types с включёнными nullable-аннотациями System.Text.Json по умолчанию не проверяет и не гарантирует их ненулевую инициализацию при десериализации из JSON — если JSON содержит `null` для свойства, аннотированного как non-nullable `string`, десериализатор просто присвоит `null` в runtime (аннотация не создаёт runtime-проверку без явной дополнительной настройки типа `JsonSerializerOptions` с валидацией/required-свойств).

Ресурсы: [Nullable reference types — MS Learn](https://learn.microsoft.com/en-us/dotnet/csharp/nullable-references) · [Nullable value types](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/nullable-value-types)

## 15. Современный C# (9–13): records, pattern matching и др.

### 15.1. Что такое `record` и какую проблему он решает по сравнению с обычным `class`?
`record` (C# 9) — тип с автоматически сгенерированной value-based семантикой равенства (`Equals`/`GetHashCode` сравнивают по значениям всех свойств, а не по ссылке), автоматическим `ToString()` с перечислением свойств, и поддержкой `with`-выражений для неразрушающего копирования с изменением отдельных свойств. Решает проблему многословного ручного написания value-equality и immutable-копирования для DTO/доменных объектов-значений.
```csharp
public record Point(int X, int Y);
var p1 = new Point(1, 2);
var p2 = p1 with { Y = 5 }; // новый объект, X=1, Y=5
Console.WriteLine(p1 == p2); // false — сравнение по значению
```

### 15.2. Чем positional record отличается от record с обычными свойствами?
Positional record (`record Point(int X, int Y);`) генерирует primary constructor, public init-only свойства (`X`, `Y`), `Deconstruct`-метод — всё автоматически из списка параметров. Record с обычными свойствами (`record Point { public int X { get; init; } }`) даёт больше контроля (валидация в setter'ах, дополнительная логика), но требует больше кода вручную. Оба получают одинаковую value-based equality/`ToString`/`with` от компилятора.

### 15.3. Что такое `init`-свойства (C# 9) и чем они отличаются от `readonly`/обычного `set`?
`init` позволяет присваивать значение свойству только во время инициализации объекта (в конструкторе или object initializer при создании), но не после — в отличие от `readonly`-поля (присваивается только в конструкторе, без object initializer), `init` совместим с синтаксисом `new T { Prop = value }`, при этом оставаясь неизменяемым после создания объекта.

### 15.4. Как работает pattern matching в C# (type patterns, property patterns, positional patterns, relational patterns)?
Type pattern: `if (obj is string s)`. Property pattern: `if (order is { Status: OrderStatus.Shipped, Total: > 100 })`. Positional pattern (для records/типов с `Deconstruct`): `if (point is (0, 0))`. Relational patterns (C# 9): `if (age is >= 18 and < 65)`. Все они комбинируются через логические паттерны `and`/`or`/`not` для выразительных условий без вложенных `if`.

### 15.5. Что такое switch expressions (C# 8) и чем они лучше классического `switch` statement?
Switch expression возвращает значение напрямую (`var result = x switch { 1 => "one", 2 => "two", _ => "other" };`), компактнее классического `switch` (нет `break`, нет case-меток как отдельных строк), поддерживает pattern matching во всех метках, и компилятор проверяет исчерпываемость (exhaustiveness) — например, для enum без `_`-паттерна выдаст предупреждение, если не все значения перечислены.

### 15.6. Что такое top-level statements (C# 9) и как они меняют структуру `Program.cs`?
Позволяют писать код точки входа приложения без явного объявления класса `Program` и метода `Main` — компилятор сам генерирует их за кулисами. Упрощает структуру простых приложений/скриптов и файл конфигурации ASP.NET Core Minimal API, но для среднего/крупного приложения обычно всё равно выносят логику в отдельные классы/методы, оставляя `Program.cs` только точкой конфигурации и запуска.

### 15.7. Что такое file-scoped namespaces (C# 10)?
`namespace MyApp.Services;` (без фигурных скобок и вложенного блока) — сокращает уровень вложенности на один при условии, что весь файл принадлежит одному namespace, уменьшая визуальный шум по сравнению с классическим `namespace X { ... }`, охватывающим всё содержимое файла.

### 15.8. Что такое global using directives (C# 10)?
`global using System;` в отдельном файле (обычно `GlobalUsings.cs`) делает using-директиву доступной во всех файлах проекта без необходимости повторять её в каждом файле — уменьшает дублирование стандартных using'ов (`System`, `System.Linq` и т.п.) по всему проекту. Может комбинироваться с implicit usings (`<ImplicitUsings>enable</ImplicitUsings>` в csproj), автоматически подключающими типичный набор namespace'ов по типу проекта.

### 15.9. Что такое primary constructors для классов (C# 12), и чем они отличаются от positional record?
C# 12 расширил primary constructors на обычные `class`/`struct` (не только record): `class Point(int x, int y) { public int X => x; }` — параметры конструктора доступны во всём теле класса как приватные "захваченные" значения. В отличие от record, primary constructor у обычного класса НЕ генерирует автоматически свойства, `Equals`/`GetHashCode`/`ToString`/`with` — только сокращает объявление конструктора и делает параметры доступными полям/методам класса.

### 15.10. Что такое `required` члены и как они сочетаются с primary constructors/records?
`required` (C# 11) обязывает инициализировать свойство при создании объекта через object initializer, независимо от того, как объявлен конструктор — компилятор проверяет на этапе компиляции, что вызывающий код обязательно указал значение, устраняя необходимость writing нескольких перегрузок конструктора только ради обязательности одних свойств при опциональности других.

### 15.11. Что такое collection expressions (C# 12, `[1, 2, 3]`)?
Единый унифицированный синтаксис создания коллекций разных типов: `int[] a = [1, 2, 3]; List<int> l = [1, 2, 3]; Span<int> s = [1, 2, 3];`, включая spread-оператор `..` для разворачивания другой коллекции внутрь литерала (`[..existing, 4, 5]`). Компилятор сам выбирает наиболее эффективный способ построения конкретного целевого типа коллекции под капотом.

### 15.12. Что такое `using` alias для произвольных типов (C# 12, `using Point = (int X, int Y);`)?
Позволяет создать псевдоним для любого типа, включая tuple-типы, generic-инстанциации, массивы (`using IntPairList = System.Collections.Generic.List<(int, int)>;`) — не только для namespace/простого класса, как раньше — упрощает чтение кода с часто повторяющимися сложными generic/tuple типами.

### 15.13. Как устроены nullable/pattern-based null checks (`is null`, `is not null`) и почему они предпочтительнее `== null`?
`is null`/`is not null` использует pattern matching, который нельзя перегрузить/переопределить пользовательским `operator ==` — гарантированно проверяет именно null, а не какую-то кастомную логику сравнения, которую тип мог бы определить через `operator ==` (что иногда приводит к неожиданному поведению `== null`, если оператор переопределён некорректно). Это делает `is null` более надёжным и предсказуемым идиоматичным способом проверки на C# 7+.

### 15.14. Что такое `with`-выражения для record struct — работают ли они так же, как для record class?
Да, `with` работает одинаково для обоих: создаёт новую копию объекта (для record class — новый объект в heap с обновлёнными свойствами, для record struct — новую копию значения на стеке/в контейнере), не изменяя исходный экземпляр — семантика "неразрушающая мутация" (non-destructive mutation) идентична, различие только в том, что физически копируется (ссылка vs значение).

### 15.15. Что такое `ArgumentNullException.ThrowIfNull` и другие Throw-helpers (.NET 6+)?
Набор статических хелперов (`ArgumentNullException.ThrowIfNull(x)`, `ArgumentOutOfRangeException.ThrowIfNegative(x)` и т.д.), заменяющих ручной `if (x == null) throw new ArgumentNullException(nameof(x));` одной строкой — компилятор дополнительно распознаёт такие вызовы для null-flow-анализа (после вызова `ThrowIfNull(x)` компилятор считает `x` non-null в оставшейся части метода).

### 15.16. Что такое паттерн list patterns (C# 11, `[1, 2, .., var last]`)?
Позволяет сопоставлять и деконструировать массивы/списки по структуре, включая точное число элементов, конкретные значения на определённых позициях, и slice-паттерн `..` для "остальных элементов" (`if (arr is [1, 2, .. var rest])`).

### 15.17. Что такое статические абстрактные члены интерфейсов (static abstract members, C# 11) помимо generic math?
Позволяют интерфейсу объявлять статические члены (методы, операторы, свойства), обязательные для реализации в implementing-типе — раньше интерфейсы могли содержать только instance-члены. Помимо generic math (см. 8.7), используются для паттернов вроде "фабричного метода, объявленного контрактом интерфейса" (`static abstract T Parse(string s)`), что позволяет писать generic-код, создающий экземпляры типов через единообразный статический контракт.

### 15.18. Как выбрать между record, class и struct при проектировании нового типа данных в 2025+?
Record class — для immutable доменных объектов/DTO с value-equality, где важна читаемость и не критична каждая аллокация. Record struct — то же самое, но для маленьких, часто копируемых значений, где важно избежать heap-аллокаций. Обычный class — для объектов с изменяемым состоянием, идентичностью (entity, а не value object), сложным поведением. Struct — для маленьких, часто используемых value types без необходимости value-equality "из коробки" через record (либо если равенство не нужно вовсе).

## 16. Entity Framework Core

### 16.1. Чем `DbContext` отличается от `DbSet<T>`, и каков их жизненный цикл в веб-приложении?
`DbContext` — представляет сессию работы с БД: отслеживает изменения (change tracking), управляет соединением и транзакциями, кэширует загруженные сущности (identity map в рамках своего времени жизни). `DbSet<T>` — представление конкретной таблицы/сущности внутри контекста, точка входа для запросов и добавления/удаления сущностей этого типа. В ASP.NET Core `DbContext` обычно регистрируется как Scoped-сервис — один экземпляр на HTTP-запрос, что предотвращает шаринг change tracker между несвязанными запросами.

### 16.2. Что такое change tracking в EF Core и как он работает?
При загрузке сущностей через `DbContext` (не с `AsNoTracking()`) EF Core сохраняет "снимок" исходных значений и следит за изменениями свойств сущности; при вызове `SaveChanges()` сравнивает текущее состояние с исходным снимком и генерирует соответствующие `UPDATE`/`INSERT`/`DELETE` SQL-запросы только для реально изменённых сущностей/свойств. Отслеживание имеет накладные расходы по памяти и CPU, поэтому для read-only сценариев рекомендуется отключать его через `AsNoTracking()`.

### 16.3. Когда использовать `AsNoTracking()` и как это влияет на производительность?
Для запросов только на чтение (без последующего `SaveChanges()` для этих сущностей) — `AsNoTracking()` отключает создание snapshot'ов и добавление сущностей в change tracker, снижая потребление памяти и ускоряя выполнение запроса, особенно для больших наборов результатов. Использовать нельзя (точнее, не имеет смысла) там, где сущность потом будет изменена и сохранена через тот же контекст.

### 16.4. Что такое миграции (Migrations) в EF Core и как они работают?
Механизм версионирования схемы БД, синхронизированный с изменениями моделей C#: `Add-Migration`/`dotnet ef migrations add` генерирует класс миграции с методами `Up`/`Down`, описывающими изменения схемы (создание/изменение таблиц, столбцов, индексов) на основе разницы между текущей моделью и последним "снапшотом" модели. `Update-Database`/`dotnet ef database update` применяет накопленные миграции к реальной БД последовательно.

### 16.5. Как решить N+1 problem в EF Core (см. также 5.3)?
Явная жадная загрузка через `.Include(x => x.Orders).ThenInclude(o => o.Items)` для загрузки связанных сущностей одним (или несколькими batched) SQL-запросом вместо одного дополнительного запроса на каждую связанную сущность отдельно, либо явная проекция сразу нужных данных через `.Select(...)` в один комбинированный запрос без отдельной загрузки навигационных свойств вовсе.

### 16.6. Чем eager loading (`Include`), lazy loading и explicit loading отличаются друг от друга?
Eager loading — связанные данные загружаются сразу вместе с основным запросом через `Include`. Lazy loading — навигационное свойство подгружается автоматически (отдельным запросом) только при первом реальном обращении к нему в коде (требует proxy-классов и включения `UseLazyLoadingProxies`) — удобно, но легко приводит к скрытым N+1 проблемам, если не осознавать, где именно происходит обращение. Explicit loading — ручной вызов `context.Entry(entity).Collection(x => x.Orders).Load()` в нужный момент, явный контроль без автоматической магии lazy loading.

### 16.7. Что такое `IQueryable` composition и почему важно не вызывать `.ToList()` слишком рано?
Каждый LINQ-оператор над `IQueryable<T>` (`.Where`, `.OrderBy`, `.Select`) лишь достраивает Expression Tree, не выполняя запрос — вызов `.ToList()`/`.ToArray()`/`await .ToListAsync()` материализует запрос, транслируя накопленное дерево выражений целиком в единый SQL-запрос. Если вызвать `.ToList()` слишком рано (например, до фильтрации), вся таблица выгрузится в память приложения, а последующие `.Where`/`.OrderBy` выполнятся уже в LINQ to Objects — теряется вся польза от трансляции в эффективный SQL на стороне БД.

### 16.8. Как EF Core обрабатывает транзакции и что такое `SaveChanges()` "из коробки"?
Каждый вызов `SaveChanges()` по умолчанию оборачивает все накопленные изменения в одну неявную транзакцию БД — либо все операции применяются успешно, либо ни одна (атомарность в рамках одного вызова). Для координации нескольких `SaveChanges()`/операций в одной логической транзакции используется явный `context.Database.BeginTransaction()`/`IDbContextTransaction`.

### 16.9. Что такое optimistic concurrency control в EF Core (`[ConcurrencyCheck]`, `RowVersion`)?
Механизм обнаружения конфликтов одновременного изменения одной строки БД разными пользователями/процессами без блокировок на чтение: свойство, помеченное `[Timestamp]`/`RowVersion` (или `[ConcurrencyCheck]`), включается в условие `WHERE` при `UPDATE`/`DELETE` — если значение в БД изменилось с момента загрузки сущности (кто-то другой успел сохранить свои изменения раньше), затронутых строк окажется 0, и EF Core бросит `DbUpdateConcurrencyException`, сигнализируя о конфликте для последующей обработки (например, повторной попытки или уведомления пользователя).

### 16.10. Как EF Core транслирует LINQ-запросы в SQL, и что произойдёт, если использовать неподдерживаемый метод?
Провайдер (например, Npgsql/SqlServer provider) анализирует Expression Tree запроса и переводит распознаваемые LINQ/C#-конструкции в соответствующие SQL-эквиваленты. Если используется метод/выражение, которое провайдер не умеет транслировать (произвольный сложный C#-метод), EF Core (начиная с EF Core 3.0) бросит исключение времени выполнения, а не тихо выполнит часть запроса в памяти (как было в устаревшем client-side evaluation до EF Core 3.0, что было признано анти-паттерном из-за скрытой деградации производительности).

### 16.11. Что такое проекция (`.Select(...)`) в контексте EF Core и почему она эффективнее загрузки полных сущностей?
Проекция позволяет запросить только нужные столбцы (переведётся в SQL `SELECT` с конкретным списком колонок вместо `SELECT *`-эквивалента для всей сущности со всеми навигационными связями) — снижает объём передаваемых данных по сети, объём материализуемых объектов в памяти, и полностью обходит change tracking (так как результат — не полноценная отслеживаемая сущность, а DTO/анонимный тип).

### 16.12. Что такое value conversions в EF Core и зачем они нужны?
Позволяют определить, как значение C#-свойства преобразуется в значение колонки БД и обратно (например, хранение `enum` как `string` в БД вместо числового кода, шифрование значения перед сохранением, сериализация сложного объекта в JSON-колонку) — без изменения формы самой модели домена в C#-коде, вся логика преобразования инкапсулирована в конфигурации маппинга.

### 16.13. Как EF Core обрабатывает наследование (TPH, TPT, TPC)?
TPH (Table Per Hierarchy) — вся иерархия классов хранится в одной таблице с discriminator-колонкой, различающей тип строки (по умолчанию в EF Core, самый производительный вариант для чтения, но с "разреженными" nullable-колонками для свойств, специфичных отдельным подтипам). TPT (Table Per Type) — отдельная таблица для каждого класса иерархии, связанные через общий первичный ключ (требует JOIN при запросах, но более нормализованная схема). TPC (Table Per Concrete class, EF Core 7+) — отдельная таблица для каждого конкретного (неабстрактного) класса без JOIN, с дублированием общих колонок в каждой таблице.

### 16.14. Что такое compiled queries / `EF.CompileQuery` и зачем они нужны?
Позволяют один раз скомпилировать Expression Tree запроса в делегат, переиспользуемый многократно без повторного разбора LINQ-выражения на каждый вызов — снижает CPU-накладные расходы трансляции запроса в SQL для очень часто выполняемых, идентичных по структуре запросов в высоконагруженных сценариях (обычно EF Core сам кэширует скомпилированные запросы внутренне, `EF.CompileQuery` даёт дополнительный явный контроль/выигрыш в узких горячих путях).

### 16.15. Как правильно организовать доступ к `DbContext` в многопоточном/параллельном коде?
`DbContext` не потокобезопасен — один экземпляр нельзя использовать одновременно из нескольких потоков/параллельных задач без внешней синхронизации (например, параллельный `Task.WhenAll` с несколькими запросами через один `DbContext` бросит исключение о конкурентном использовании). Решение — создавать отдельный `DbContext` (через `IDbContextFactory<TContext>`) для каждой параллельной операции, либо выполнять запросы к БД строго последовательно в рамках одного контекста.

## 17. Dependency Injection и IoC

### 17.1. В чём разница между Inversion of Control (IoC) и Dependency Injection (DI)?
IoC — общий принцип: контроль над созданием/связыванием объектов передаётся из самого объекта внешнему коду/фреймворку (инверсия обычного потока управления, когда объект сам создаёт свои зависимости через `new`). DI — конкретная техника реализации IoC: зависимости передаются объекту извне (через конструктор, свойство или метод), а не создаются им самостоятельно. IoC-контейнер (например, встроенный `Microsoft.Extensions.DependencyInjection`) — инструмент, автоматизирующий создание графа объектов с их зависимостями по конфигурации регистраций.

### 17.2. Чем отличаются Constructor Injection, Property Injection и Method Injection?
Constructor Injection — зависимости передаются через параметры конструктора, наиболее предпочтительный способ (делает зависимости явными и обязательными, объект невозможно создать в невалидном состоянии без зависимостей). Property Injection — зависимость устанавливается через публичное свойство после создания объекта, используется для опциональных зависимостей. Method Injection — зависимость передаётся как параметр конкретного метода, а не хранится в объекте — используется, когда зависимость нужна только для одной операции, а не всего времени жизни объекта.

### 17.3. Какие есть жизненные циклы (lifetimes) сервисов в `Microsoft.Extensions.DependencyInjection`, и в чём разница?
`Transient` — новый экземпляр при каждом запросе из контейнера. `Scoped` — один экземпляр в пределах одного scope (в ASP.NET Core — один HTTP-запрос). `Singleton` — один экземпляр на всё время жизни приложения, общий для всех потребителей.

```
Singleton: ─────────────────────────────────────▶ (весь процесс)
Scoped:    [Request 1: ───▶]  [Request 2: ───▶]  [Request 3: ───▶]
Transient: [→][→] [→]  [→][→]  [→]                 (новый на каждый запрос из DI)
```

### 17.4. Что такое "captive dependency" антипаттерн?
Ситуация, когда сервис с более "долгим" временем жизни (например, Singleton) захватывает зависимость с более "коротким" временем жизни (Scoped/Transient) через конструктор — захваченная Scoped-зависимость фактически "застревает" со временем жизни Singleton (живёт вечно, не обновляется между запросами), что часто приводит к использованию устаревших данных или к утечке ресурсов, рассчитанных на короткую жизнь (например, `DbContext`, живущий вечно вместо одного запроса). Контейнер по умолчанию (в ASP.NET Core с `ValidateScopes: true` в Development) обнаруживает и бросает ошибку на такое несоответствие.

### 17.5. Как правильно внедрять Scoped-зависимость в Singleton-сервис, если это действительно нужно?
Через `IServiceScopeFactory`/`IServiceProvider`, внедрённый в Singleton — Singleton-сервис вручную создаёт новый scope (`using var scope = _scopeFactory.CreateScope();`) каждый раз, когда ему нужно получить актуальный экземпляр Scoped-зависимости (например, в фоновой задаче `IHostedService`, которая должна периодически обращаться к `DbContext`), вместо захвата Scoped-сервиса напрямую через конструктор.

### 17.6. Что такое Service Locator паттерн, и почему он считается антипаттерном по сравнению с DI?
Service Locator — объект получает зависимости, явно запрашивая их у центрального реестра/контейнера внутри своего кода (`serviceProvider.GetService<IFoo>()`), а не получая их извне через конструктор. Считается антипаттерном, потому что скрывает реальные зависимости класса (их не видно в сигнатуре конструктора — "скрытые зависимости"), усложняет unit-тестирование (нужен настоящий или замоканный контейнер вместо простой подстановки объектов в конструктор) и создаёт неявную связанность с самим контейнером.

### 17.7. Как DI-контейнер разрешает граф зависимостей (dependency graph) и обнаруживает циклические зависимости?
Контейнер рекурсивно разрешает каждую зависимость конструктора запрашиваемого типа, строя дерево создания объектов "снизу вверх" — если в процессе разрешения он снова встречает уже разрешаемый (ещё не завершённый) тип в текущей цепочке, это цикл, и контейнер бросает исключение (циклические зависимости невозможно корректно разрешить через constructor injection, так как ни один из двух объектов не может быть создан первым без готовой ссылки на другой) — решение обычно в пересмотре дизайна (выделение общей зависимости в третий сервис, либо разрыв цикла через lazy-инъекцию `Func<IFoo>`/`Lazy<IFoo>`).

### 17.8. Чем встроенный DI-контейнер ASP.NET Core отличается от сторонних (Autofac, Ninject и др.), когда стоит использовать сторонний?
Встроенный контейнер лёгкий, быстрый, покрывает базовые сценарии (три lifetime, конструкторная инъекция, generic-регистрации). Сторонние контейнеры добавляют продвинутые возможности: property injection "из коробки", более гибкие сценарии условной регистрации (child containers, именованные регистрации нескольких реализаций одного интерфейса с явным выбором по имени), interception/AOP, более детальную диагностику графа зависимостей. Стоит переходить на сторонний, если проект реально упирается в отсутствующую в стандартном контейнере возможность, а не "про запас".

### 17.9. Что такое `IOptions<T>`, `IOptionsSnapshot<T>`, `IOptionsMonitor<T>` — в чём разница?
Все три — механизмы типизированного доступа к конфигурации через DI. `IOptions<T>` — Singleton, значение считывается один раз при старте и не меняется в течение работы приложения. `IOptionsSnapshot<T>` — Scoped, пересчитывается заново на каждый scope (запрос), отражая изменения конфигурации между запросами (например, при hot-reload конфиг-файла). `IOptionsMonitor<T>` — Singleton, но с поддержкой уведомлений об изменениях (`OnChange`) и получением актуального значения в реальном времени даже из Singleton-сервисов, без пересоздания scope.

### 17.10. Как тестировать классы, использующие DI, без поднятия реального контейнера?
Обычно unit-тесты вообще не используют DI-контейнер — тестируемый класс создаётся напрямую (`new MyService(mockDependency)`), с зависимостями, подменёнными на mock/stub объекты (через Moq/NSubstitute) или упрощённые тестовые реализации интерфейсов, передаваемые прямо в конструктор — DI-контейнер нужен лишь для "монтирования" реального графа приложения в runtime/integration-тестах (`WebApplicationFactory` в ASP.NET Core), не для unit-уровня.

### 17.11. Что такое multiple implementations of the same interface и как их разрешать через DI?
Контейнер поддерживает регистрацию нескольких реализаций одного интерфейса (`services.AddTransient<INotifier, EmailNotifier>(); services.AddTransient<INotifier, SmsNotifier>();`) — при инъекции `IEnumerable<INotifier>` потребитель получает все зарегистрированные реализации сразу (полезно для паттерна "цепочка обработчиков"/broadcast всем подписчикам). При обычной инъекции одиночного `INotifier` вернётся последняя зарегистрированная реализация — для явного выбора конкретной реализации по ключу нужны либо фабрики (`Func<string, INotifier>`), либо (начиная с .NET 8) keyed services (`AddKeyedTransient`).

### 17.12. Что такое конструкторная перегрузка (multiple constructors) и как DI-контейнер выбирает, какой использовать?
Встроенный контейнер `Microsoft.Extensions.DependencyInjection` выбирает конструктор с наибольшим числом параметров, которые он может полностью разрешить среди зарегистрированных сервисов — если несколько конструкторов одинаково разрешимы, контейнер бросает исключение неоднозначности (в отличие от некоторых сторонних контейнеров, которые могут поддерживать явные атрибуты выбора конструктора). Рекомендуемая практика — иметь только один публичный конструктор для DI-разрешаемых классов, чтобы избежать неоднозначности.

Ресурсы: [Dependency injection — MS Learn](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection) · [DI guidelines](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection-guidelines)

## 18. ASP.NET Core: конвейер запросов и middleware

### 18.1. Как устроен конвейер обработки HTTP-запроса (middleware pipeline) в ASP.NET Core?
Запрос последовательно проходит через цепочку зарегистрированных middleware-компонентов, каждый из которых может выполнить логику до вызова следующего (`await next(context)`), после него, либо вообще прервать конвейер (не вызвав `next`), сформировав ответ самостоятельно (short-circuiting). Порядок регистрации middleware в `Program.cs` (`app.Use...`) определяет порядок выполнения — критично важен (например, `UseAuthentication` должен идти раньше `UseAuthorization`, `UseRouting` — раньше обоих).

```
Request → [Exception Handling] → [HTTPS Redirect] → [Routing] → [Auth] → [Endpoint] 
Response ← [Exception Handling] ← [HTTPS Redirect] ← [Routing] ← [Auth] ← [Endpoint]
```

### 18.2. Как написать собственный middleware — через класс или через inline-делегат?
Inline (быстрый способ, для простой логики): `app.Use(async (context, next) => { /* до */ await next(context); /* после */ });`. Класс-конвенция (для более сложной, тестируемой, DI-совместимой логики): класс с конструктором, принимающим `RequestDelegate next` (и опционально другие DI-сервисы через конструктор), и методом `InvokeAsync(HttpContext context, ...)`, зарегистрированный через `app.UseMiddleware<MyMiddleware>()`.

### 18.3. Чем `IMiddleware` (factory-based) отличается от конвенционного middleware (по сигнатуре методов)?
Конвенционный middleware создаётся один раз при старте приложения (per-request-independent instance с DI только через конструктор, singleton-подобное поведение самого middleware-объекта). `IMiddleware` — явный интерфейс с методом `InvokeAsync`, создаваемый через DI-контейнер на каждый запрос заново (если зарегистрирован с не-Singleton lifetime) — позволяет безопасно внедрять Scoped-зависимости прямо в конструктор middleware, чего конвенционный подход не гарантирует без осторожности (там Scoped-зависимости обычно передаются через параметр метода `InvokeAsync`, а не конструктор).

### 18.4. Чем Minimal API отличается от Controller-based подхода в ASP.NET Core?
Minimal API (введён в .NET 6) определяет endpoints напрямую через лямбды/делегаты (`app.MapGet("/users/{id}", (int id) => ...)`), без обязательной иерархии классов-контроллеров, атрибутов маршрутизации и MVC-инфраструктуры — меньше boilerplate-кода для простых API/микросервисов. Controller-based (MVC) даёт больше встроенной структуры (фильтры действий, модельная валидация через атрибуты, соглашения именования, лучше подходит для крупных API с большим числом связанных эндпоинтов) — выбор зависит от масштаба и предпочтений команды по организации кода.

### 18.5. Что такое filters (Action Filters, Exception Filters, Authorization Filters) в MVC, и как они соотносятся с middleware?
Filters — механизм MVC-уровня для внедрения сквозной логики (cross-cutting concerns) вокруг выполнения конкретных action-методов контроллеров (валидация модели, логирование, обработка исключений конкретно на уровне MVC-конвейера), выполняются внутри middleware `UseEndpoints`/routing-middleware, уже после того как запрос сматчился на конкретный контроллер/action — middleware же работает на более общем уровне HTTP-конвейера, до/вне зависимости от конкретного MVC-маршрута.

### 18.6. Что такое model binding и model validation в ASP.NET Core?
Model binding — автоматическое преобразование данных запроса (route values, query string, form data, JSON body) в параметры action-метода/модель на основе их имён и атрибутов (`[FromBody]`, `[FromQuery]`, `[FromRoute]`). Model validation — автоматическая проверка data annotation-атрибутов модели (`[Required]`, `[Range]`, `[StringLength]`) после binding, результат которой доступен через `ModelState.IsValid` (в контроллерах) — при использовании `[ApiController]`-атрибута невалидная модель автоматически приводит к ответу `400 Bad Request` без явной ручной проверки в каждом action.

### 18.7. Как работает routing в ASP.NET Core (attribute routing vs conventional routing)?
Conventional routing определяет общий шаблон маршрута централизованно (`app.MapControllerRoute("default", "{controller}/{action}/{id?}")`), применяемый ко всем контроллерам без явных атрибутов на каждом action. Attribute routing задаёт маршрут явно через атрибуты прямо на контроллере/методе (`[Route("api/[controller]")]`, `[HttpGet("{id}")]`) — даёт более явный и гибкий контроль над конкретными URL, преобладающий подход в Web API проектах.

### 18.8. Что такое `IHostedService`/`BackgroundService` и для чего они используются?
Интерфейс/базовый класс для запуска долгоживущей фоновой логики внутри процесса ASP.NET Core приложения (или любого generic host), управляемой жизненным циклом хоста (`StartAsync`/`StopAsync`) — используется для фоновых задач: обработка очередей сообщений, периодические задания, слушатели событий, не привязанные к конкретному HTTP-запросу. `BackgroundService` упрощает реализацию, требуя переопределения только одного метода `ExecuteAsync(CancellationToken)`.

### 18.9. Как ASP.NET Core обрабатывает CORS (Cross-Origin Resource Sharing)?
Middleware `UseCors()` с настроенной политикой (`AllowAnyOrigin`/конкретные origins, `AllowAnyMethod`/конкретные HTTP-методы, `AllowAnyHeader`/конкретные заголовки) добавляет соответствующие CORS-заголовки (`Access-Control-Allow-Origin` и др.) к ответам, разрешая браузеру у клиента на другом origin (домене/порту/схеме) выполнять запросы к API — важно располагать `UseCors` в правильном месте конвейера (после `UseRouting`, до `UseAuthorization`/эндпоинтов) и не использовать `AllowAnyOrigin` вместе с credentials в продакшене по соображениям безопасности.

### 18.10. Что такое health checks в ASP.NET Core и зачем они нужны в микросервисной архитектуре?
`Microsoft.Extensions.Diagnostics.HealthChecks` предоставляет стандартизированный механизм проверки состояния приложения и его зависимостей (доступность БД, внешних сервисов, очередей) через выделенный HTTP-эндпоинт (`/health`), опрашиваемый оркестраторами (Kubernetes liveness/readiness probes, балансировщиками нагрузки) для автоматического принятия решений о перезапуске нездоровых инстансов или временном исключении их из ротации трафика.

### 18.11. Как работает конфигурация (`IConfiguration`) и её приоритет источников (appsettings.json, переменные окружения, secrets)?
`IConfiguration` объединяет несколько источников в единую иерархическую структуру ключ-значение, применяемых по умолчанию в порядке возрастания приоритета: `appsettings.json` → `appsettings.{Environment}.json` → User Secrets (только Development) → переменные окружения → аргументы командной строки — источники, добавленные позже, переопределяют одноимённые ключи из более ранних, что позволяет, например, переопределять настройки через переменные окружения в продакшене/контейнерах без изменения файлов конфигурации.

### 18.12. Что такое `HttpClientFactory` и почему не стоит создавать `new HttpClient()` напрямую на каждый запрос?
Прямое создание `new HttpClient()` на каждый вызов приводит к исчерпанию доступных сокетов (socket exhaustion) — каждый `HttpClient` держит собственный пул соединений, а частое создание/уничтожение (особенно с `using`) не даёт TCP-соединениям корректно закрыться (они зависают в состоянии `TIME_WAIT`) под нагрузкой. `IHttpClientFactory` управляет пулом переиспользуемых `HttpMessageHandler`, корректно ротируя их (учитывая DNS-изменения через периодическое пересоздание handler'ов), предоставляя именованные/типизированные клиенты с централизованной настройкой (базовый URL, заголовки, Polly-политики retry/circuit breaker) через DI.

## 19. Производительность и оптимизация

### 19.1. Как правильно профилировать производительность C#-приложения перед оптимизацией?
Сначала измерить, а не гадать: инструменты вроде `dotnet-trace`, `dotnet-counters`, Visual Studio Profiler, PerfView или BenchmarkDotNet для точечных микробенчмарков — находят реальные "горячие точки" (hot paths), где действительно тратится время/память, вместо интуитивной оптимизации "на глаз", которая часто оптимизирует не то место и усложняет код без реального выигрыша ("preliminary optimization is the root of all evil").

### 19.2. Что такое BenchmarkDotNet и зачем он нужен вместо ручного замера через `Stopwatch`?
Библиотека для точных микробенчмарков, автоматически решающая проблемы наивного замера через `Stopwatch` (прогрев JIT перед замером, устранение влияния GC пауз, множественные итерации со статистическим анализом, изоляция каждого бенчмарка в отдельном процессе) — ручной `Stopwatch`-замер часто даёт искажённые результаты из-за JIT-компиляции "на лету" первого вызова, эффектов GC, и недостаточного числа повторений для статистической значимости.

### 19.3. Как boxing влияет на производительность в реальных сценариях (например, `string.Format`)?
Каждая value type-переменная, переданная в параметр типа `object` (например, `params object[] args` в старых перегрузках `string.Format`/логирования), боксится — создаётся объект в heap. При частом логировании/форматировании с числовыми параметрами в горячих путях это создаёт заметное давление на GC; современные API логирования (`ILogger` с source-generated logging, .NET 6+) и `string.Format`/интерполяция с `DefaultInterpolatedStringHandler` избегают этого через generic-перегрузки без boxing.

### 19.4. Что такое struct vs class с точки зрения производительности — когда struct действительно быстрее?
Struct эффективнее, когда: объект маленький (обычно рекомендуется ≤16-24 байта), короткоживущий, часто создаётся в больших количествах (массив struct — непрерывный блок памяти без косвенных ссылок и без отдельных heap-аллокаций на каждый элемент, лучшая cache locality). Struct может быть медленнее, если он большой (копирование при каждой передаче по значению дороже копирования ссылки) или часто передаётся между методами без `in`/`ref` (много defensive copies).

### 19.5. Что такое false sharing и как оно связано с многопоточностью?
Ситуация, когда несколько потоков независимо изменяют разные переменные, которые физически попадают в одну и ту же cache line CPU (обычно 64 байта) — несмотря на логическую независимость данных, аппаратный протокол когерентности кэша (cache coherency) заставляет ядра постоянно инвалидировать и перезагружать эту cache line друг у друга, резко снижая производительность параллельного кода. Решается padding'ом (искусственным выравниванием структур, чтобы разделяемые разными потоками поля попадали в разные cache lines).

### 19.6. Как избежать лишних аллокаций в горячих путях (hot paths) кода?
Основные техники: `Span<T>`/`ReadOnlySpan<T>` вместо создания подмассивов/подстрок, `ArrayPool<T>`/`ObjectPool<T>` для переиспользования буферов вместо повторного `new`, struct вместо class для маленьких короткоживущих данных, избегание LINQ в самых горячих циклах (LINQ создаёт промежуточные итераторы/делегаты с накладными расходами по сравнению с обычным `for`-циклом), кэширование делегатов/замыканий вместо их пересоздания на каждый вызов.

### 19.7. Что такое `in`-параметры и когда они реально дают выигрыш в производительности?
`in` передаёт struct-параметр по ссылке (без копирования всей структуры), гарантируя вызывающему коду, что метод не изменит переданное значение (readonly reference) — выигрыш заметен только для достаточно больших struct (маленькие struct типа `int`/`Point` копируются быстрее, чем разыменование ссылки, поэтому `in` для них может быть даже медленнее из-за defensive copies компилятора при обращении к членам, если struct не `readonly`).

### 19.8. Как работает devirtualization (девиртуализация) JIT-компилятором и как её стимулировать?
Если JIT может статически доказать, что виртуальный вызов метода всегда разрешается в одну конкретную реализацию (например, тип `sealed`, либо через профильно-управляемую оптимизацию/tiered compilation JIT видит, что в runtime всегда вызывается один и тот же конкретный тип), он заменяет дорогой виртуальный вызов (через v-table) на прямой (inline-совместимый) вызов — заметно быстрее. Стимулируется через `sealed class`/`sealed override` там, где переопределение точно не потребуется в будущем.

### 19.9. Что такое tiered compilation и tiered PGO (Profile-Guided Optimization) в современном .NET JIT?
JIT сначала компилирует метод быстро, но с минимальными оптимизациями (Tier 0) для быстрого старта, а для "горячих" (часто вызываемых) методов позже перекомпилирует их с полными оптимизациями (Tier 1), основываясь на реально собранной статистике использования в runtime (Tiered PGO, .NET 8+ включён по умолчанию) — балансирует между быстрым временем старта приложения и максимальной пропускной способностью для реально нагруженного кода, без необходимости заранее гадать, что будет "горячим".

### 19.10. Как оптимизировать сериализацию JSON по производительности (например, `System.Text.Json` vs `Newtonsoft.Json`)?
`System.Text.Json` спроектирован с прицелом на производительность и минимальные аллокации (использует `Utf8JsonReader`/`Utf8JsonWriter` поверх `Span<byte>` без промежуточных строковых буферов, поддерживает source-generated сериализаторы через `[JsonSerializable]` для AOT-совместимой и ещё более быстрой сериализации без рефлексии) — как правило заметно быстрее и менее прожорлив по памяти, чем `Newtonsoft.Json`, хотя последний исторически богаче фичами/гибкостью настройки для сложных сценариев.

### 19.11. Что такое memory-mapped files и когда они полезны для производительности?
Позволяют отобразить файл (или его часть) напрямую в виртуальное адресное пространство процесса (`MemoryMappedFile`), избегая явного копирования данных между буферами приложения и ОС при чтении/записи — эффективны для обработки очень больших файлов, доступа к общей памяти между процессами, случайного доступа к произвольным участкам большого файла без загрузки его целиком в обычную managed-память.

### 19.12. Как измерить и снизить количество Gen0/Gen1/Gen2 сборок мусора в приложении?
Измеряется через `dotnet-counters` (счётчики `gc-heap-size`, `gen-0-gc-count` и т.д.) или `GC.CollectionCount(generation)` программно. Снижается через уменьшение частоты и объёма аллокаций (см. 19.6), переиспользование объектов вместо создания новых, избегание ненужного boxing, правильный выбор структур данных (struct вместо class для маленьких недолговечных объектов), настройку Server GC для throughput-ориентированных приложений на многоядерных серверах.

Ресурсы: [Performance — MS Learn](https://learn.microsoft.com/en-us/dotnet/framework/performance/) · [BenchmarkDotNet docs](https://benchmarkdotnet.org/) · [Memory management best practices](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/performance)

## 20. Тестирование (Unit Testing, Mocking)

### 20.1. В чём разница между unit-тестом, integration-тестом и end-to-end (e2e) тестом?
Unit-тест проверяет один изолированный "модуль" кода (обычно один класс/метод) с полностью подменёнными внешними зависимостями (БД, сеть, файловая система) — быстрый, детерминированный, узкий по охвату. Integration-тест проверяет взаимодействие нескольких реальных компонентов вместе (например, реальный доступ к тестовой БД) — медленнее, но проверяет реальную стыковку частей системы. E2E-тест проверяет полный пользовательский сценарий через весь реально развёрнутый стек (UI/API до БД) — самый медленный и хрупкий, но даёт наибольшую уверенность в работоспособности системы целиком.

### 20.2. Что такое AAA-паттерн (Arrange-Act-Assert) в написании unit-тестов?
Структурный подход к организации тела теста: Arrange — подготовка тестовых данных, объектов, моков. Act — вызов тестируемого метода/действия. Assert — проверка полученного результата на соответствие ожидаемому. Чёткое разделение улучшает читаемость и понятность теста без необходимости вникать в логику для определения, что именно тестируется.

### 20.3. Чем mock отличается от stub, fake и spy (test doubles)?
Stub — простая заглушка, возвращающая заранее заданные значения без проверки того, как её вызывали. Mock — объект, который не только заменяет реальную зависимость, но и явно проверяет, что определённые методы были вызваны с определёнными аргументами определённое число раз (behavior verification). Fake — упрощённая, но реально работающая альтернативная реализация (например, in-memory база данных вместо реальной СУБД). Spy — обёртка вокруг реального объекта, записывающая информацию о вызовах, при этом делегирующая реальному объекту фактическое выполнение.

### 20.4. Какие популярные фреймворки для unit-тестирования в .NET и чем они отличаются?
xUnit, NUnit, MSTest — фреймворки для написания и запуска тестов (test runner + assertion API + атрибуты `[Fact]`/`[Test]`/`[TestMethod]`). xUnit — наиболее популярен в современных .NET-проектах, создаёт новый экземпляр тестового класса на каждый тест по умолчанию (изоляция состояния между тестами без общего `[SetUp]`). NUnit/MSTest используют явные атрибуты `[SetUp]`/`[TestInitialize]` для подготовки состояния перед каждым тестом, разделяя экземпляр класса между тестами иначе.

### 20.5. Как правильно использовать Moq/NSubstitute для мокирования зависимостей?
Создаётся мок-объект интерфейса зависимости, настраивается ожидаемое поведение конкретных методов (`mock.Setup(x => x.GetUser(1)).Returns(testUser);` в Moq), передаётся в конструктор тестируемого класса вместо реальной реализации — после теста можно проверить (`mock.Verify(x => x.SaveUser(It.IsAny<User>()), Times.Once);`), что определённый метод был вызван ожидаемое число раз с ожидаемыми аргументами, подтверждая корректность взаимодействия тестируемого кода с зависимостью.

### 20.6. Почему сложно/нежелательно мокировать конкретные классы (concrete classes) вместо интерфейсов?
Мокирование конкретного класса требует, чтобы мокируемые методы были `virtual` (иначе большинство мок-фреймворков не может их переопределить через наследование/proxy), что вынуждает делать методы виртуальными исключительно ради тестируемости (загрязняя дизайн production-кода деталями тестирования). Интерфейсы изначально спроектированы как контракт для подмены реализации, что естественно совместимо с любым мок-фреймворком без дополнительных требований к дизайну класса.

### 20.7. Что такое Test-Driven Development (TDD) и цикл Red-Green-Refactor?
TDD — практика написания теста до написания реализации: Red (написать падающий тест для ещё не существующей функциональности) → Green (написать минимальный код, чтобы тест прошёл) → Refactor (улучшить код, сохраняя тесты зелёными). Даёт побочный эффект — код изначально проектируется тестируемым (низкая связанность, чёткие интерфейсы), а не адаптируется под тесты постфактум.

### 20.8. Как тестировать асинхронный код (`async`/`await` методы)?
Тестовый метод сам объявляется `async Task` (не `async void` — тестовые фреймворки не могут дождаться завершения `async void`-метода и не увидят исключения из него), и внутри используется `await` для вызова тестируемого асинхронного метода — большинство современных тестовых фреймворков (xUnit, NUnit) нативно поддерживают `async Task` тестовые методы, дожидаясь их завершения перед определением результата теста.

### 20.9. Что такое параметризованные тесты (`[Theory]` в xUnit, `[TestCase]` в NUnit)?
Позволяют запускать один и тот же тестовый метод многократно с разными наборами входных данных без дублирования кода теста для каждого случая — `[Theory]` в xUnit комбинируется с `[InlineData(1, 2, 3)]` для задания конкретных наборов аргументов, либо с `[MemberData]`/`[ClassData]` для более сложных/генерируемых наборов тестовых данных.

### 20.10. Как тестировать код, зависящий от `DateTime.Now`/текущего времени?
Прямое использование `DateTime.Now`/`DateTime.UtcNow` делает код недетерминированным и сложным для тестирования (результат зависит от момента запуска теста). Решение — абстрагировать источник времени через внедряемый интерфейс (`ITimeProvider`/встроенный в .NET 8 `TimeProvider`), позволяющий подменить "текущее время" фиксированным значением в тесте, делая тест детерминированным и воспроизводимым.

Ресурсы: [Unit testing best practices — MS Learn](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-best-practices) · [xUnit docs](https://xunit.net/) · [Testing in .NET](https://learn.microsoft.com/en-us/dotnet/core/testing/)

## 21. Сериализация

### 21.1. Чем `System.Text.Json` отличается от `Newtonsoft.Json (Json.NET)`?
`System.Text.Json` — встроенная в .NET (с .NET Core 3.0) библиотека, спроектированная для высокой производительности и низких аллокаций (см. 19.10), поддерживает source generators для AOT/trimming-совместимой сериализации без рефлексии. `Newtonsoft.Json` — сторонняя, но исторически стандартная де-факто библиотека с более богатым набором возможностей "из коробки" (более гибкие `JsonConverter`, поддержка `LINQ to JSON` через `JObject`/`JToken`, более снисходительная обработка нестандартного JSON) — выбор часто определяется необходимостью специфичных фич Newtonsoft или требованиями существующей кодовой базы.

### 21.2. Как настроить кастомную сериализацию через `JsonConverter` в `System.Text.Json`?
Наследовать `JsonConverter<T>`, переопределить методы `Read`(десериализация через `Utf8JsonReader`) и `Write` (сериализация через `Utf8JsonWriter`), зарегистрировать конвертер через атрибут `[JsonConverter(typeof(MyConverter))]` на типе/свойстве, либо глобально через `JsonSerializerOptions.Converters`.

### 21.3. Что такое циклические ссылки при сериализации и как их обрабатывать?
Если объект A ссылается на B, а B ссылается обратно на A (например, навигационные свойства EF Core сущностей в обе стороны), сериализатор по умолчанию либо бросит исключение о превышении глубины (StackOverflow/MaxDepth exceeded), либо зациклится бесконечно. Решения: `ReferenceHandler.Preserve` (System.Text.Json) добавляет специальные `$id`/`$ref`-метаданные для представления циклов в JSON, `[JsonIgnore]` на одном направлении навигационного свойства, либо (предпочтительнее для публичных API) явная проекция в DTO без циклических ссылок вообще.

### 21.4. В чём разница между бинарной, XML и JSON сериализацией по применимости?
JSON — наиболее распространён для Web API/межсервисного взаимодействия благодаря компактности, читаемости человеком и универсальной поддержке во всех языках/платформах. XML — используется реже для новых API (более многословен), но остаётся стандартом в некоторых корпоративных/legacy-интеграциях (SOAP, некоторые B2B-протоколы), поддерживает схемы валидации (XSD) "из коробки". Бинарная сериализация (например, Protobuf, MessagePack) — компактнее и быстрее обеих, но не читаема человеком без специальных инструментов, используется во внутренних высокопроизводительных межсервисных коммуникациях (gRPC), где важна скорость и размер payload.

### 21.5. Почему BinaryFormatter считается устаревшим/опасным и что использовать вместо него?
`BinaryFormatter` признан небезопасным (уязвим к атакам через десериализацию произвольных типов из недоверенного источника, что может привести к удалённому выполнению кода — deserialization gadget attacks) и удалён/заблокирован по умолчанию в современных версиях .NET. Альтернативы: `System.Text.Json` для JSON, Protobuf/MessagePack для компактной бинарной сериализации с явным контролем допустимых типов и без риска произвольной десериализации.

### 21.6. Как работает контроль версий (versioning) при сериализации, если схема данных меняется со временем?
Общие стратегии: добавление новых полей всегда должно быть опциональным (default-значение при отсутствии в старых данных), не переиспользовать/не менять смысл существующих полей, использовать явные версии контракта (например, разные namespace/маршруты API для v1/v2), либо инструменты вроде Protobuf, изначально спроектированные с обратной/прямой совместимостью полей "из коробки" (числовые теги полей вместо имён, опциональные поля по умолчанию).

Ресурсы: [System.Text.Json overview — MS Learn](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/overview) · [BinaryFormatter security guide](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide)

## 22. Безопасность в .NET

### 22.1. Что такое SQL injection и как EF Core/параметризованные запросы защищают от него?
SQL injection — внедрение вредоносного SQL-кода через непроверенный пользовательский ввод, конкатенируемый напрямую в текст SQL-запроса (`"SELECT * FROM Users WHERE Name = '" + input + "'"`), позволяющий злоумышленнику изменить логику запроса. EF Core (и параметризованные `SqlCommand` с `@param`) по умолчанию передаёт пользовательские значения как отдельные параметры запроса (а не встраивает их в текст SQL), что делает такой ввод безопасным — движок БД трактует параметр строго как данные, а не как исполняемый код, независимо от его содержимого.

### 22.2. Как правильно хранить пароли пользователей — почему нельзя хранить их в открытом виде или через обычный хэш?
Пароли должны храниться только в виде хэша, вычисленного специализированным медленным алгоритмом с солью (salt), устойчивым к перебору (bcrypt, PBKDF2, Argon2 — не обычные быстрые хэши вроде MD5/SHA-256, которые легко перебираются brute-force/rainbow tables на современном оборудовании из-за своей скорости). ASP.NET Core Identity использует PBKDF2 с солью и настраиваемым числом итераций по умолчанию для хэширования паролей.

### 22.3. В чём разница между аутентификацией (Authentication) и авторизацией (Authorization)?
Аутентификация — процесс подтверждения личности пользователя ("кто вы?", вход по логину/паролю, токену, сертификату). Авторизация — процесс проверки прав уже аутентифицированного пользователя на выполнение конкретного действия/доступа к ресурсу ("что вам разрешено?"). В ASP.NET Core это middleware `UseAuthentication()` (должен идти раньше) и `UseAuthorization()` соответственно.

### 22.4. Что такое JWT (JSON Web Token) и из каких частей он состоит?
Компактный, самодостаточный токен для передачи утверждений (claims) между сторонами, состоящий из трёх частей, разделённых точками и закодированных в Base64Url: Header (алгоритм подписи и тип токена), Payload (claims — данные о пользователе/правах, время истечения), Signature (криптографическая подпись первых двух частей секретным/приватным ключом, позволяющая проверить, что токен не был подделан/изменён после выдачи). Важно: payload не зашифрован (просто закодирован), поэтому не следует помещать в JWT секретные данные без дополнительного шифрования.

### 22.5. Что такое CSRF (Cross-Site Request Forgery) и как ASP.NET Core защищает от него?
Атака, при которой злоумышленник заставляет браузер аутентифицированного пользователя незаметно отправить запрос на уязвимый сайт (используя автоматически прикладываемые cookie сессии) от его имени без ведома пользователя. ASP.NET Core защищает через anti-forgery токены (`[ValidateAntiForgeryToken]`, автоматически для Razor Pages/MVC форм) — уникальный токен, встраиваемый в форму и проверяемый на сервере, которого злоумышленник не может знать заранее и подделать в кросс-доменном запросе.

### 22.6. Что такое XSS (Cross-Site Scripting) и как Razor защищает от него по умолчанию?
Атака, при которой злоумышленник внедряет вредоносный JavaScript-код через ввод, который затем без должного экранирования отображается в HTML-странице другим пользователям (выполняясь в их браузере в контексте доверенного сайта). Razor по умолчанию автоматически HTML-кодирует (escaping) все значения, выводимые через `@variable`, превращая потенциально опасные символы (`<`, `>`, `"`) в безопасные HTML-сущности — явный обход через `@Html.Raw()` необходим только тогда, когда содержимое заведомо доверенное, и должен применяться крайне осторожно.

### 22.7. Что такое Secrets Management, и почему нельзя хранить строки подключения/API-ключи в `appsettings.json` в git-репозитории?
Секреты в открытом виде в репозитории доступны всем, у кого есть доступ к коду (включая историю git даже после удаления файла) — утечка секретов через публичные/скомпрометированные репозитории — одна из частых причин security-инцидентов. Решения: User Secrets (`dotnet user-secrets`) для локальной разработки (хранится вне репозитория на диске разработчика), Azure Key Vault/AWS Secrets Manager/HashiCorp Vault для продакшена, переменные окружения, внедряемые системой оркестрации (Kubernetes secrets) — секреты никогда не должны попадать в систему контроля версий.

### 22.8. Что такое principle of least privilege в контексте настройки приложения/БД-доступа?
Принцип наименьших привилегий — каждому компоненту/пользователю/сервисному аккаунту должны выдаваться только те права, которые реально необходимы для его функции, не больше (например, сервисный аккаунт приложения для чтения отчётов не должен иметь прав на `DROP TABLE` в БД) — минимизирует потенциальный ущерб при компрометации конкретного компонента, ограничивая "радиус поражения" одной скомпрометированной учётной записи/сервиса.

Ресурсы: [Security in ASP.NET Core — MS Learn](https://learn.microsoft.com/en-us/aspnet/core/security/) · [OWASP Top 10](https://owasp.org/www-project-top-ten/) · [Secrets management](https://learn.microsoft.com/en-us/aspnet/core/security/app-secrets)
